# src-tauri/src/export/remap_spans.rs

Where each clip's frames begin in `TimeMap::frame_plan`. `frame_bounds(i, fps)` already floors the start when `i == 0` and floors the end when `i + 1 == segs.len()`, and uses the half-open ceil rule (`ceil(start)`, `ceil(end) - 1`) at every interior join; once `TimeMap::build` emits clips in OUTPUT order (Batch 1), segment 0 IS the first segment of the first surviving clip and the last segment IS the last segment of the last surviving clip, so that existing rule already reads as the right per-clip rule: **the map's outer edges floor, every other edge - a cut, a speed edge, a clip join - is the half-open ceil split.** No change to `frame_bounds` or `frame_plan` was needed for this; this module only reads them.

Two consequences, both pinned below. **A split is lossless.** Splitting a range in two, in order, produces exactly the plan the unsplit range produced, whether or not the split instant lands on a frame boundary - the strongest guard available on the frame rule, and what makes Split (`edit::ops::clipops::SplitAt`) a safe operation. **A reorder always duplicates the splice frame, and keeps the frame count only when the take's start and end are aligned the same way.** For a take `[S, E)` split at `M` and reordered to `[M, E)` then `[S, M)` (`S'`/`M'`/`E'` below are each bound `* fps / 1000`): the unsplit (or in-order) plan is `floor(E') - floor(S') + 1` entries, its one run of segments flooring both outer ends; the reordered plan's first clip is no longer the LAST segment, so it ceils its end instead of flooring it, and its second clip is no longer the FIRST, so it ceils its start instead of flooring it, `[ceil(E') - floor(M')] + [floor(M') - ceil(S') + 1] = ceil(E') - ceil(S') + 1` entries once the shared `floor(M')` cancels - which it does for any split point, a second face of the same losslessness. Two things then move independently: the splice frame `floor(M')` is always shown twice, once closing the new-last clip and once opening the new-first one, a flat gain of one entry; the take's own first frame is lost whenever the START sits off a frame boundary, since the clip holding it is no longer first and so ceils its start rather than flooring it; and the take's own last frame is lost whenever the END sits exactly ON one, since the clip holding it is no longer last and so ceils-then-drops-one from its end rather than flooring it.

The net, `ceil(E') - ceil(S') + 1` against `floor(E') - floor(S') + 1`, is `+1` when only the end is unaligned, `-1` when only the start is, and `0` when both are aligned or both are off - the frame count is never a function of the end alone. The two-clip reorder pinned below has `500 ms` and `9000 ms` both exactly on a 10 fps frame (5 and 90), so nothing is lost at either end and the totals match exactly (86 and 86). The same take started at `517 ms` instead of `500` (frame 5.17, only the start unaligned, the end still exactly frame 90) drops the take's own first frame and is one frame SHORTER reordered than not, 85 against 86. A real 2507 ms take at 60 fps starts aligned (frame 0) but ends on 150.42, only the end unaligned, so nothing is lost and the duplicated splice frame alone makes it one frame LONGER reordered, 152 against 151. That is a sub-frame artefact of a rule that must keep both the trim-in frame and the recording's final frame for the ordinary (unsplit) case, and it is accepted rather than fixed: avoiding it needs `full_dur_ms` carried onto every segment, for a frame nobody will see.

Mirrored by `clipSpans` in `src/shared/math/remapPlan.ts` (`docs/api/src/shared/math/remapPlan.md`); the parity table lives in `remap_spans_tests.rs` and `remapClips.test.ts`.

## ClipSpan

```rust
pub struct ClipSpan { pub clip: usize, pub plan_start: usize, pub plan_len: usize, pub first_k: u64 }
```

One run of `plan_len` consecutive `frame_plan(fps)` entries that all belong to the same clip. `clip` is `Segment.clip` - the ORIGINAL index into `doc.clips` as written, so a dropped clip (inverted, empty, or wholly cut away) simply leaves a gap in the indices this carries, exactly as `Segment` itself already promises. `plan_start` indexes `frame_plan(fps)` at the SAME `fps` the span was built with; it means nothing against a plan built at a different rate. `first_k` is `frame_plan(fps)[plan_start]`, carried so a caller (the export's per-clip decoder spawn) does not have to index back into the plan just to seek its decoder to the right recording frame.

## TimeMap::clip_spans

```rust
pub fn clip_spans(&self, fps: u64) -> Vec<ClipSpan>
```

Walks `segments()` in order with the same `frame_bounds` arithmetic and the same per-segment entry count `frame_plan` uses (`floor((k_end - k_start) / factor) + 1`), and merges a segment into the previous span when its `clip` matches the one before it - a clip cut into several segments by a mid-clip cut or speed span still reports as ONE span, because the export spawns one decoder per CLIP, not per segment. A segment `frame_bounds` returns `None` for (no frames at this `fps`) contributes nothing and is skipped outright, so a clip can vanish from the list entirely. Whether a clip CAN vanish depends on its position, not only its length: the first segment of a multi-segment map floors its start and only ceils its end, and integer arithmetic guarantees that combination is never empty for a non-empty source range, so the FIRST clip in output order always shows at least one frame no matter how short it is. A later clip has no such guarantee and can disappear at a low enough `fps` (`a_clip_that_contributes_no_frames_gets_no_span`).

The spans partition the plan: contiguous, covering every `frame_plan(fps)` entry exactly once, in order (`the_spans_partition_the_plan`, checked across three fixtures and four frame rates). Batch 4's two consumers: the export's per-clip decoder spawn (one seek per span, not per segment) and the dissolve's boundary instant (the last entry of a span and the first of the next).

### Behaviors

- `an_empty_clip_list_is_one_span_covering_the_whole_plan` - no clips is the trim as one span: `plan_len` 85 at 10 fps, `first_k` 5 (the floored trim-in).
- `a_split_in_order_reproduces_the_unsplit_plan_exactly` - splitting `[500,9000)` into two clips at 4000, once on a frame boundary and once 50 ms off it, reproduces the unsplit 86-entry plan exactly both times, and the two spans meet where the split does (35/51 entries aligned, 36/50 off).
- `a_reorder_keeps_the_frame_count_and_moves_the_splice_frame` - swapping the two clips keeps the plan at 86 entries, but the frame at the old join (90) is dropped and the frame at the new join (40) opens both spans.
- `the_clips_fixtures_spans_line_up_with_its_seventy_entry_plan` - the shared clips fixture's two spans (49 and 21 entries) sum to its 70-entry plan, and its `plan_boundaries` (49, 54) shows the clip join needs a decoder seek but the cut at 54 does not (same clip on both sides).
- `a_clip_that_contributes_no_frames_gets_no_span` - a 1 ms clip placed LAST still lands a frame at 60 fps but not at 3 fps (its 500..501 window straddles no multiple of the ~333 ms frame period), leaving one span, `clip: 0`, `plan_start: 0` - deliberately not the first clip in the list, since a first clip can never be empty (see above).
- `the_spans_partition_the_plan` - on the plain, clips and reordered fixtures, at 10/24/30/60 fps, every span's `plan_start` is the running total of the previous spans' `plan_len`, `first_k` matches the plan at that index, and the total lands exactly on the plan's length.
