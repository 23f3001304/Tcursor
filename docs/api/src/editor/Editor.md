# src/editor/Editor.tsx

The post-record editor: loads `edit.json` via IPC, owns all shared editor state, and composes `TopBar`, `Rail`, an inspector/panel, `Stage`, `Transport`, and `Timeline`. The preview plays the recording natively (`Stage`) and applies the exact camera curve (`cameraTrack`) as a transform, so it is smooth 60fps; edits go through the Edit API and `rev` bumps so the camera curve refetches.

## Editor

```tsx
export function Editor({ folder, onClose }: { folder: string; onClose: () => void }): JSX.Element
```

Renders the editor layout and manages the editing lifecycle for one recording.

### Props

- `folder: string` - absolute path to the project directory. *Why:* every IPC call (load, preview tracks, autoedit, export) takes the folder as its key.
- `onClose: () => void` - return to the HUD. *Why:* the editor does not own the window/view switch; the parent does.

### Behavior

**Preview data (effects keyed per source).**
- `cameraTrack` and `previewLayout` are fetched on `[folder, rev]` - they depend on the timeline, so they refetch when an edit bumps `rev`.
- `clickTrack`, `spotlightHolds`, and `previewBg` are fetched on `[folder]` only - clicks and recorded holds are immutable and the background doesn't change with the current op set, so refetching them on every edit was part of the add-effect lag and was removed.
- `cursorKinds` and the timeline media (`ensureThumbs`, `ensureWaveform` x2, `ensurePreviewAudio`) are fetched once per `[folder]`. `cursorSprites` is fetched on `[folder, doc?.settings.cursor.pack]` instead of `rev` - it re-decodes only when the selected cursor pack actually changes (picking a different pack, or importing one, in `CursorPanel`), not on every unrelated edit.
- `getProjectManifest` is fetched once per `[folder]` into `preprocessed` - whether `preprocess_project` (run from the HUD's "Saving..." step right after a recording stops) already built this project's editor-preview media. It gates the proxy fetch below. The other timeline-media calls (`ensureThumbs`/`ensureWaveform`/`ensurePreviewAudio`) stay unconditional regardless of `preprocessed` - they are `generate_once`-cached on the Rust side and already cheap once preprocessing has produced their files; only the proxy transcode is expensive AND unambiguous enough (no "was this track even recorded" guessing) to skip outright on the frontend.

**Fast load (`[folder, quality]`).** On an already-`preprocessed` project AT the default quality (`DEFAULT_PROXY_HEIGHT`, 720), points `srcUrl` straight at the known proxy path - no transcode, no `ensureProxy` round trip. Otherwise (a legacy/un-preprocessed project, a failed preprocessing pass, or the user picked a non-default quality via the Transport toggle) shows the raw capture instantly (`video.mp4`) so the preview appears with no transcode wait, then hot-swaps `srcUrl` to the light proxy once `ensureProxy` finishes (for smoother scrubbing). Playback is paused first so the `src` remount can't restart from 0.

**Playback.** Driven by the native `<video>` in `Stage`, which reports its time via `onTime`; `onTime` sets `timeMs` and stops playback at `resolveTrim(doc?.trim, dur).outMs` - the trim's resolved out point, not just the clip end, so play never runs into a trimmed-out tail. At the boundary it parks `timeMs` *exactly* on `outMs` (not the frame or two of overshoot the video reports before the pause lands), so the playhead sits on the line rather than past it. There is no RAF playhead loop in the editor. `dur` is the `<video>`'s real duration (`vidDurMs`) when known, else `doc.trim.out_ms` - the encoded length can differ from the seeded timeline span, so the video's own duration is the source of truth for the playhead end. Scrubbing the timeline itself is unrestricted (only `onPlay`, below, respects the trim start).

**Trim + aspect (passed to `Transport`).** `trimRange = resolveTrim(doc.trim, dur)` and `trimmed = trimRange.inMs > 0 || trimRange.outMs < dur` are computed once per render and passed down as `trimmed`/`onResetTrim` (clears `SetTrim` back to `{0,0}`). `Transport`'s `onPlay` wrapper snaps `timeMs` to `trimRange.inMs` first when starting playback from outside `[inMs, outMs)`. `doc.aspect`/`SetAspect` are passed straight through as `aspect`/`onAspect`. The actual trim RANGE is set by dragging `TrimOverlay`'s edge handles on the `Timeline`, not from `Transport`. `exporting` (from `useEditorData`) is also passed through as `Transport`'s `exporting` prop (Task 36) - `Transport` locks its play/trim/aspect controls while an export is running, so nothing changes underfoot mid-render.

**Export events (`[]`, via `useEditorData`).** Subscribes to `export-progress` / `export-done` / `export-error`; unsubscribes on unmount. `export-done` sets `exportDone` and stores its payload (the exported file's own path) into `exportPath`; `export-error` captures its payload into `exportError` (`exportDone`/`exportError`/`exportPath` all cleared back to their "no outcome yet" state whenever a new export starts, or - see `ExportDialog.md` - whenever its dialog is CLOSED while showing that outcome; NOT on open, since an export can finish in the background while the dialog is closed and reopening it must still show the result). `TopBar`'s Export button (`onOpenExport`) only opens `showExportDialog` - the actual `exportProject(folder, settings)` call, and the `exporting`/`pct`/`exportDone`/`exportError`/`exportPath` reset, happen in the `onExport` callback passed to `ExportDialog`.

**`docRef`.** A `useRef` mirroring `doc`, reassigned (`docRef.current = doc;`) on every render. Every closure that gets deferred through `enqueue` (`applyOp`, `onRun`, and - via the `docRef` passed into `useEditHistory` - `swap`) reads `docRef.current` at its own EXECUTION time rather than closing over whatever `doc` was at the render that created it. This matters specifically because the queue can delay a call: while `applyOp` #1 awaits its IPC round trip, `doc` (the React state) has not changed yet, so a SECOND control fired during that window (another `applyOp` call, or `undo`/`redo`) would capture that same stale pre-#1 `doc` if it closed over the value directly - `docRef.current`, read once the queue actually reaches that task (i.e. after #1's `setDoc` has landed and React has re-rendered), reflects the real current doc instead.

**`applyOp(op)`.** `enqueue`s (see `opQueue.ts`) a closure that records the pre-edit doc (`docRef.current`, not a captured `doc`), persists one edit op via `applyEditOp`, swaps in the returned doc, and bumps `rev` - except for ops whose name ends in `_effect` (add/update/remove effect), which skip the bump because effects don't change the camera/layout/clicks/bg (this is why adding or dragging a spotlight is instant rather than laggy; the preview reflects effects straight from the returned doc). Routing through `enqueue` means a call that arrives while a previous `applyOp` (or an `undo`/`redo`, or the AI director's `onRun`) is still in flight does not start until that previous one has settled - see `enqueue` below.

**`enqueue`.** One `createQueue()` instance (`useRef`, stable for the editor's lifetime), shared by `applyOp`, `onRun`, and - via the `enqueue` parameter passed into `useEditHistory` - `undo`/`redo`. Serializes every `EditDoc` mutation into one call order, so an undo/redo issued while an `applyOp` (or the whole AI reveal pass) is still in flight reverts the doc that mutation actually settled to, instead of racing it.

**Zoom aiming (`aimOn` / `aimPoint` / `aimMode` / `aimAt` / `onMoveMode`).** A Region-target zoom (`ZoomTarget::Fixed`) stores a 0..1 screen-content aim point, and `Stage` can place it directly on the preview. `aimPoint` = `zoomTargetPoint(selected zoom's target)`, so it is `null` unless a Region zoom is selected - which makes it double as "is aiming even possible right now". `aimMode` = `aimOn && !moveMode && !!aimPoint`.

The `!moveMode` term is the mutual-exclusion rule the two stage gestures need: camera Move mode and zoom aiming both claim the same pointer on the same canvas. It is deliberately a **suppression**, not a cancellation - turning Move mode on (`onMoveMode`, the wrapper actually passed down as `requestMoveMode`) clears `aimOn` outright, but Move mode being on merely hides aiming, so nothing here can trigger `useMoveModeGuard`'s destructive "turn Move off and delete your keyframes" dialog as a side effect of wanting to aim a zoom. `ZoomInspector` disables its Aim button in that state and says why. Switching the rail tab also clears `aimOn`, since it clears the selection.

`aimAt(x, y)` is the commit: a plain `update_zoom { target: { fixed: { x, y } } }` through `applyOp`. Reticle drags call it on every pointer move and rely on `useEditHistory`'s `COALESCE_MS` window to fold the burst into one undo step - no new undo machinery.

**`addZoom` / `addSpotlight` / `addCameraMove` / `zoomAt`.** From `useTimelineActions(applyOp, timeMs, setSel, setPlaying)` (`src/editor/hooks/useTimelineActions.ts`, Task 36 - kept out of `Editor` so it stays under the line limit, mirroring `useTrimActions`). `addZoom`/`addSpotlight`/`addCameraMove` add a 2s zoom / spotlight, or a centered camera-move keyframe (`x:0.5, y:0.5, size:0.25`), at the playhead and select it. `zoomAt(x, y)` is the click-to-zoom handler passed to `Stage`: pauses, adds a full zoom (`add_zoom_full`), then sets its target to the clicked 0..1 screen point (`update_zoom` with `{ fixed: { x, y } }`) and selects it.

**`onRun()`.** Runs the AI director. `running` is checked and set to `true` SYNCHRONOUSLY, before anything is enqueued (`if (!doc || running) return; setRunning(true); ...`) - this also disables the Transport wand button (`aiRunning` prop) immediately, so a second click can't even reach the guard check, let alone enqueue a second overlapping run. The whole pass then runs inside ONE `enqueue(...)` call - a single queue task from the queue's point of view - wrapping `director.run(...)` (from `useDirector()`, `src/editor/director/useDirector.ts`), with `setRunning(false)` chained onto that call's own `.finally(...)` so `running` (and the wand's `disabled`) stays true for the task's ACTUAL full duration, not just until `enqueue` was called. `director.run` performs EXACTLY the statements the pre-Task-25 inline loop did, in the same order (`record(doc0)` once, then per step: raw `applyEditOp` + `setDoc` + `rev` bump + narration log + (for `add_zoom_full`) scrub the playhead) - it just also choreographs the fake pointer (`DirectorOverlay`, mounted below) around that sequence and returns how many steps actually landed, so `onRun`'s caller can tell a cancelled run from a completed one. Previously each step applied raw and OUTSIDE the queue, so an undo issued between two reveal steps could execute immediately and then be silently overwritten by the very next step's `setDoc` - `enqueue`-ing the whole pass closes that window: an undo/redo issued mid-run is itself queued behind it and only runs once the pass has fully settled. See `director/useDirector.md` for the choreography itself (fake-pointer moves/presses, cancel, progress).

**`saveDocSettings` / `onAutoModel`.** From `useDocSettings(folder, doc, setDoc, record, setRev)` (`src/editor/hooks/useDocSettings.ts`) - `saveDocSettings` records an undo step before writing a patched `settings` object (passed to `EditorPanels` for every settings-editing panel); `onAutoModel` writes the same way but WITHOUT recording an undo step, and is passed to `AiPanel` alone for its mount-time auto-default-model effect.

**Media retry.** `retryMedia` (from `useEditorData`) is passed straight through to `Stage` as `onRetryMedia`, wired to `StageMedia`'s error-card Retry button.

**`brandState` (Task 39 - the living brand mark).** `!doc.settings.ui.animated_brand ? "idle" : exporting ? "exporting" : running ? "directing" : "idle"` - computed once per render and passed to `TopBar` (which forwards it, plus `pct`, straight to `TcursorMark`). The doc's OWN `ui.animated_brand` (a per-recording settings snapshot, same field family as `doc.settings.cursor.pack`) gates the state entirely off before `TcursorMark` ever sees anything but `"idle"`; `exporting` wins over `directing` if both were somehow true (can't actually happen today - the AI director doesn't run mid-export). See `src/lib/brandWave.md` for the `MarkState` mapping and `TcursorMark.md` for the animation itself.

**Loading guard.** Renders "Loading edit..." until `doc` resolves.

**Layout.** `ResizeEdges` (frameless-window grips), `TopBar`, then `e-body` containing `Rail`, `EditorPanels` (the inspector/panel router), and `Stage` wrapped in a `.e-stagetoast` div (anchors the undo/redo `Toast` bottom-center of the stage without `Stage.tsx` itself needing toast state); then `DirectorOverlay` (the AI director's fake pointer + cancel scrim/Stop pill, `running`/`director.planning`/`doc.settings.ai_model || undefined` (as `model`)/`director.pointerRef`/`director.progress`/`director.requestCancel` - a sibling of `e-body`, per its own spec; `planning`/`model` are Task 40's planning-phase cancel UX, see `director/useDirector.md`), `Transport`, `Timeline`, `moveOffDialog`, `ExportDialog`, `ShortcutsOverlay` (`showShortcuts`, toggled by `useEditorKeymap`'s `?` shortcut via `onOverlay`), and `EditorSettingsDialog` (Task 35 - `showSettings`, toggled by `TopBar`'s gear button via `onOpenSettings`; `settings={doc.settings}` and `onSaveSettings={saveDocSettings}` so its writes are undoable like every other settings panel; its own `onOpenShortcuts` closes this dialog and opens `ShortcutsOverlay` instead of stacking two modals).

### Notes

- `quality` cycles 480→720→1080 and re-runs the proxy effect (initialized to `DEFAULT_PROXY_HEIGHT`, the same 720 `preprocess_project` transcodes ahead of time); `muted` toggles the preview `<audio>`.
- `proj` is the last path segment of `folder`, shown by `TopBar`.
- `showExportDialog` is the only export-dialog state `Editor` owns itself; `exporting`/`pct`/`exportDone`/`exportError` are all lifted from `useEditorData` and passed straight through to `ExportDialog`.
- `showShortcuts` is the analogous local state for `ShortcutsOverlay` - toggled by `useEditorKeymap`'s `onOverlay` callback (fires when `keyAction` returns `"overlay"`, i.e. the `?` key) and cleared by the overlay's own `onClose` (scrim click or Escape).
- `showSettings` (Task 35) is the analogous local state for `EditorSettingsDialog` - toggled by `TopBar`'s gear button (`onOpenSettings`) and cleared by the dialog's own `onClose` (scrim click or Escape), same shape as `showExportDialog`/`showShortcuts`.
- `toast` / `onSwap` / `dismissToast` come from `useUndoToast()` (`src/editor/shell/Toast.tsx`); `onSwap` is handed to `useEditHistory` and fires once per actual undo/redo swap (keyboard or button).
