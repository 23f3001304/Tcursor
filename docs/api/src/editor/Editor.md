# src/editor/Editor.tsx

The post-record editor: loads `edit.json` via IPC, owns all shared editor state, and composes `TopBar`, `EditorShell` (the customizable area tree, M1a - see `shell/ClassicShell.md`) and the modal stack. It no longer places `Stage`, `Transport`, `Timeline` or the panels itself: which of them are on screen, and where, is the active workspace's business. The preview plays the recording natively (`Stage`) and applies the exact camera curve (`cameraTrack`) as a transform, so it is smooth 60fps; edits go through the Edit API and `rev` bumps so the camera curve refetches.

## Editor

**Time remap.** `useTimeMap(doc, dur)` runs right after `dur` is known and puts `map` and `outDoc` (falling back to `doc` before the first remap) into `ShellProps`; nothing else in this file knows about cuts or speed.

**`tab` (2026-09-14).** `useState<Tab | null>(() => readPanelTab(TAB_IDS))`, with one `useEffect` on `[tab]` calling `writePanelTab(tab)`. `null` is "the panel column is collapsed" - a real resting state since the column became collapsible (`shell/panelState.md`), reached by pressing the open rail tab again or by any panel's close X. It is seeded from and written back to `localStorage` (`tcursor.editor.panel`), so the editor reopens the way it was left, collapsed included; storage that throws or holds a value from another build reads as `"ai"`, never as a collapsed editor the user did not ask for. The effect is the only writer, so every path that changes the tab persists without having to remember to.

**`range` (time remap T7).** `useState<[number, number] | null>(null)` - the ruler's Shift+drag selection in clip ms, held here for the same reason `sel` is: the TIMELINE edits and draws it (`timeline/useRangeSelect.ts`, `RangeOverlay`) while the TRANSPORT acts on it (`TransportTools`' Cut and Speed 2x) and clears it afterwards, and neither area owns the other. `Editor` never reads it - it only declares it and passes `range`/`setRange` down in the bundle.

```tsx
export function Editor({ folder, onClose }: { folder: string; onClose: () => void }): JSX.Element
```

Renders the editor layout and manages the editing lifecycle for one recording.

### Props

- `folder: string` - absolute path to the project directory. *Why:* every IPC call (load, preview tracks, autoedit, export) takes the folder as its key.
- `onClose: () => void` - return to the HUD. *Why:* the editor does not own the window/view switch; the parent does.

### Behavior

**Theme (light / dark / system).** `Editor` renders the `.editor` root that `editor.css` hangs both palettes off, so the editor follows the same Preferences theme setting the recorder HUD does. `applyTheme` (`src/hud/preferences/applyTheme.ts`) stamps `data-theme="light"|"dark"` on the document root - the HUD and the editor share one window, so the attribute is already set by the time `Editor` mounts from the HUD. The dark palette is the plain `.editor` rule (the default, unchanged from before the light theme existed) and the light one is `:root[data-theme="light"] .editor`, repeated under `@media (prefers-color-scheme: light)` guarded by `:root:not([data-theme="dark"])`. That media copy is what covers the first paint of a cold start into a project (`getLaunchProject` routes straight past the HUD); since 2026-09-14 `App`'s own startup effect then applies the stored theme (`getSettings` then `applyTheme`), so an "always light"/"always dark" preference holds from the first settings read even when the HUD never mounts. The light palette was darkened on the same day after the owner found it too pale to read: the ground steps down to `#e6e7eb`, hairlines and dividers double, and every text rung (including `--e-dim`, which used to be the one grey shared with the dark theme) is a darker grey. `themeTokens.test.ts` fails the build if a token is declared in one palette and not the other, or if any editor stylesheet grows a raw hex colour outside the palette blocks.

**Preview data (effects keyed per source).**
- `cameraTrack` and `previewLayout` are fetched on `[folder, rev]` - they depend on the timeline, so they refetch when an edit bumps `rev`.
- `clickTrack`, `spotlightHolds`, and `previewBg` are fetched on `[folder]` only - clicks and recorded holds are immutable and the background doesn't change with the current op set, so refetching them on every edit was part of the add-effect lag and was removed.
- `cursorKinds` and the timeline media (`ensureThumbs`, `ensureWaveform` x2, `ensurePreviewAudio`) are fetched once per `[folder]`. `cursorSprites` is fetched on `[folder, doc?.settings.cursor.pack]` instead of `rev` - it re-decodes only when the selected cursor pack actually changes (picking a different pack, or importing one, in `CursorPanel`), not on every unrelated edit.
- `getProjectManifest` is fetched once per `[folder]` into `preprocessed` - whether `preprocess_project` (run from the HUD's "Saving..." step right after a recording stops) already built this project's editor-preview media. It gates the proxy fetch below. The other timeline-media calls (`ensureThumbs`/`ensureWaveform`/`ensurePreviewAudio`) stay unconditional regardless of `preprocessed` - they are `generate_once`-cached on the Rust side and already cheap once preprocessing has produced their files; only the proxy transcode is expensive AND unambiguous enough (no "was this track even recorded" guessing) to skip outright on the frontend.

**Fast load (`[folder, quality]`).** On an already-`preprocessed` project AT the default quality (`DEFAULT_PROXY_HEIGHT`, 720), points `srcUrl` straight at the known proxy path - no transcode, no `ensureProxy` round trip. Otherwise (a legacy/un-preprocessed project, a failed preprocessing pass, or the user picked a non-default quality via the Transport toggle) shows the raw capture instantly (`video.mp4`) so the preview appears with no transcode wait, then hot-swaps `srcUrl` to the light proxy once `ensureProxy` finishes (for smoother scrubbing). Playback is paused first so the `src` remount can't restart from 0.

**Playback.** Driven by the native `<video>` in `Stage`, which reports its time via `onTime`; `onTime` (built in `useEditorCallbacks`, see "Render hygiene" below) sets `timeMs` and stops playback at the trim's resolved out point - not just the clip end - so play never runs into a trimmed-out tail. At the boundary it parks `timeMs` *exactly* on `outMs` (not the frame or two of overshoot the video reports before the pause lands), so the playhead sits on the line rather than past it. There is no RAF playhead loop in the editor. `dur` is the `<video>`'s real duration (`vidDurMs`) when known, else `doc.trim.out_ms` - the encoded length can differ from the seeded timeline span, so the video's own duration is the source of truth for the playhead end. Scrubbing the timeline itself is unrestricted (only `onPlay`, below, respects the trim start).

**Trim + aspect (passed to `Transport`; also still passed to `Stage`, which ignores them since the look pass retired `StageToolbar` - see `stage/Stage.md`).** `trimRange = resolveTrim(doc?.trim ?? {in_ms:0,out_ms:0}, dur)` is computed once per render (mirrored into `trimRangeRef`, read by `useEditorCallbacks` - see "Render hygiene") and `trimmed = trimRange.inMs > 0 || trimRange.outMs < dur` is derived from it after the loading guard. `onPlayToggle` (built in `useEditorCallbacks`, passed to `Transport` as `onPlay`) snaps `timeMs` to `trimRange.inMs` first when starting playback from outside `[inMs, outMs)`. `doc.aspect`/`SetAspect` are passed straight through as `aspect`/`onAspect` (`onAspect` also from `useEditorCallbacks`) to BOTH `Transport` and `Stage` (`Stage` also gets `aspectLocked={exporting || dur <= 0}`, computed inline the same way `Transport`'s own `locked` is; it no longer reads either, the aspect chip in `Transport` being the editor's one aspect control now). The actual trim RANGE is set by dragging `TrimOverlay`'s edge handles on the `Timeline`, not from `Transport`. `exporting` (from `useExportState`) is also passed through as `Transport`'s `exporting` prop (Task 36) - `Transport` locks its play/trim/aspect controls, AND (bug-sweep-2 Task 8, L3) its AI-director wand, while an export is running, so nothing changes underfoot mid-render. `exporting` is likewise now passed to `EditorPanels` (→ `AiPanel`'s run button) for the same reason.

**`onTab` is gone (M1a).** It used to be `useCallback((t: Tab) => { if (t !== tab) { setSel(null); setAimOn(false); } setTab(t); }, [tab])` - one shared navigation handler for `Rail` and the since-removed `StageToolbar` that cleared the selection on every tab switch. The clearing half of that is now wrong: selection is an independent axis, so changing a panel tab must leave `sel` alone. `Editor` therefore passes plain `tab`/`setTab` down in the `SlotProps` bundle, and the shell builds the one handler the rail needs (`onTab`). Since the classic rail came back it draws the eight tabs itself (`shell/panelTabs.md`), and since the column became collapsible `ClassicShell`'s `onTab` resolves a press through `nextTab` (`shell/panelState.md`) rather than setting the tab outright.

**Esc deselects.** `keyAction` (`hooks/keymap.md`) gained a `"deselect"` action for Escape, fired only when something IS selected. `useEditorKeymap` takes a new `escOwned` flag, which `Editor` passes as `arrangeOn`: stage arrange mode owns Escape for its own exit and deliberately KEEPS the segment selected so the pill and the inspector button can re-enter, so Escape stays that surface's key while it is live.

**Export state.** `useExportState(pushToast)` (`src/editor/hooks/useExportState.ts`, Task 11 - split out of `useEditorData` to stay under that file's line budget) owns `exporting`/`pct`/`exportDone`/`exportError`/`exportPath`, subscribes to `export-progress`/`export-done`/`export-error`/`export-warning` once, and returns `startExport`/`exportStartedAt` (see `useExportState.md` for the full write-up, including why the ETA-baseline timestamp is owned there rather than inside `ExportProgress`). `pushToast` (`useUndoToast`'s `push`) is passed as the `export-warning` handler, so Rust's non-fatal export warning (webcam missing/frozen - Task 9 added the `emit`, this is the first listener) surfaces as a Toast pill instead of only reaching stderr. `TopBar`'s Export button (`onOpenExport`) only opens `showExportDialog` - the actual `exportProject(folder, settings)` call, plus `startExport()` and the `exportDone`/`exportError`/`exportPath` reset, happen in the `onExport` callback, which moved into `EditorDialogs` in T34 L3 along with the dialog itself. `Editor` now keeps only `exportState` (the whole hook return, passed through as one prop) and reads `exporting`/`exportState.pct` off it for `Transport`/`EditorPanels`/`TopBar`.

**`docRef`.** A `useRef` mirroring `doc`, reassigned (`docRef.current = doc;`) on every render. Every closure that gets deferred through `enqueue` (`applyOp`, `onRun`, and - via the `docRef` passed into `useEditHistory` - `swap`) reads `docRef.current` at its own EXECUTION time rather than closing over whatever `doc` was at the render that created it. This matters specifically because the queue can delay a call: while `applyOp` #1 awaits its IPC round trip, `doc` (the React state) has not changed yet, so a SECOND control fired during that window (another `applyOp` call, or `undo`/`redo`) would capture that same stale pre-#1 `doc` if it closed over the value directly - `docRef.current`, read once the queue actually reaches that task, reflects the real current doc instead.

*Why `applyOp` also writes `docRef.current` itself (bug-sweep-2 Task 8, M1).* The render-time mirror above is not early enough for a queued `undo`/`redo` sitting right behind an in-flight `applyOp`: `enqueue`'s chain (`opQueue.ts`) resolves the next queued task as a **microtask** the instant the apply's own promise settles, which is BEFORE React's macrotask-scheduled re-render from that apply's `setDoc` call ever runs (microtasks always drain first). So `applyOp` ALSO does `docRef.current = d` synchronously, right after `setDoc(d)`, before its own promise resolves - closing that race. Without it, a `Ctrl+Z` landing in the ~10-30ms window while an edit's `apply_edit_op` round trip is in flight would push the STALE pre-apply doc onto the redo stack instead of the real result, making that edit unrecoverable by either undo or redo. See `useEditHistory.md`'s matching section for the other half.

**`applyOp(op)`.** `enqueue`s (see `opQueue.ts`) a closure that records the pre-edit doc (`docRef.current`, not a captured `doc`; `record` returns a `RecordToken` - `null`-`snapshot` when coalesced - see `useEditHistory.md`), persists one edit op via `applyEditOp`, swaps in the returned doc (`setDoc` AND `docRef.current`, see above), and bumps `rev` - except for ops whose name ends in `_effect` (add/update/remove effect), which skip the bump because effects don't change the camera/layout/clicks/bg (this is why adding or dragging a spotlight is instant rather than laggy; the preview reflects effects straight from the returned doc). A rejected `applyEditOp` (`catch`) calls `unrecord(token)` when `token.snapshot` is non-null, so a failed apply never leaves a phantom undo step (bug-sweep-2 Task 8, L1; identity-hardened in review round 1, Important 4 - see `useEditHistory.md`). Routing through `enqueue` means a call that arrives while a previous `applyOp` (or an `undo`/`redo`, or the AI director's `onRun`) is still in flight does not start until that previous one has settled - see `enqueue` below. `useCallback`'d (deps `[enqueue, docRef, record, unrecord, folder, setDoc, setRev]`, all permanently stable) so its identity survives every render including a pure playhead tick - `applyOp` is a prop of every `React.memo`'d hot-tree component (`Timeline`, `EditorPanels`, and transitively `Stage`/`Transport` via the callbacks built from it), so an unstable `applyOp` would have defeated all of their memo on its own regardless of anything else. It's kept directly in `Editor.tsx` (not moved into `useEditorCallbacks.ts`) because several OTHER hooks need it built FIRST (`useMoveModeGuard`, `useTrimActions`, `useTimelineActions`, `useEditorCallbacks` itself for `aimAt`/`onAspect`) - see "Render hygiene" below.

**`enqueue`.** One `createQueue()` instance (`useRef`, stable for the editor's lifetime), shared by `applyOp`, `onRun`, and - via the `enqueue` parameter passed into `useEditHistory` - `undo`/`redo`. Serializes every `EditDoc` mutation into one call order, so an undo/redo issued while an `applyOp` (or the whole AI reveal pass) is still in flight reverts the doc that mutation actually settled to, instead of racing it.

**Zoom aiming (`aimOn` / `aimPoint` / `aimMode` / `aimAt` / `onMoveMode`).** A Region-target zoom (`ZoomTarget::Fixed`) stores a 0..1 screen-content aim point, and `Stage` can place it directly on the preview. `aimPoint` = `useMemo(() => zoomTargetPoint(selZoom?.target), [selZoom])` (`selZoom = doc?.zooms.find(z => z.id === sel)`) - `null` unless a Region zoom is selected, which makes it double as "is aiming even possible right now". Memoized (render hygiene pass) because `zoomTargetPoint` returns a fresh `[x, y]` array literal every call - without the `useMemo`, `aimPoint` would be a new array reference every render even when the underlying target hadn't changed, defeating `Stage`'s memo on every tick since `aimPoint` is one of its props. `aimMode` = `aimOn && !moveMode && !arrangeOn && !!aimPoint`.

**Stage arrange mode (T34 L3, `arrangeSeg` / `arrangeOn` / `onArrange`).** `useArrangeMode(doc, sel)` (`hooks/useArrangeMode.md`) owns the third exclusive stage mode: selecting a layout PILL enters it, Escape leaves it while remembering the segment, `onArrange` (`LayoutInspector`'s "Arrange on stage" button) re-enters, and deselecting exits outright. `arrangeSeg` goes to `Stage` (non-null IS the mode, and it is only ever a segment that still exists); `arrangeOn` + `onArrange` go to `EditorPanels` for the inspector, and `arrangeOn` is folded into `aimMode` above for the same reason `!moveMode` is - the three modes all claim the same canvas pointer. `Editor` also passes `applyOp` down to `Stage` for the first time, used only by arrange mode's commit-on-release. The hook is built AFTER `useEditorCallbacks` because it needs `onSeek` (it seeks into the segment on entry - see `arrangeMode.md`'s `arrangeSeekMs`), and it returns the `onSel` that `Timeline` now gets in place of a bare `setSel`, so a pill re-click is a real entry gesture rather than a no-op set.

The `!moveMode` term is the mutual-exclusion rule the two stage gestures need: camera Move mode and zoom aiming both claim the same pointer on the same canvas. It is deliberately a **suppression**, not a cancellation - turning Move mode on (`onMoveMode`, built in `useEditorCallbacks`, wrapping `requestMoveMode`) clears `aimOn` outright, but Move mode being on merely hides aiming, so nothing here can trigger `useMoveModeGuard`'s destructive "turn Move off and delete your keyframes" dialog as a side effect of wanting to aim a zoom. `ZoomInspector` disables its Aim button in that state and says why. Switching the rail tab also clears `aimOn`, since it clears the selection.

`aimAt(x, y)` (built in `useEditorCallbacks`) is the commit: a plain `update_zoom { target: { fixed: { x, y } } }` through `applyOp`. **Render hygiene pass:** a reticle drag no longer calls `aimAt` on every pointermove - `Stage` now debounces that call (trailing ~80ms, flushed on release) and drives the reticle's on-screen position from its own local optimistic state instead, exactly like `Slider.tsx` debounces its `onChange` commit (see `Stage.md`'s "Reticle drag debounce"). `useEditHistory`'s `COALESCE_MS` window still folds the resulting burst of `update_zoom`s into one undo step either way - no new undo machinery.

**`addZoom` / `addSpotlight` / `addCameraMove` / `zoomAt`.** From `useTimelineActions(applyOp, timeMsRef, docRef, setSel, setPlaying)` (`src/editor/hooks/useTimelineActions.ts`, Task 36 - kept out of `Editor` so it stays under the line limit, mirroring `useTrimActions`). `addZoom`/`addSpotlight`/`addCameraMove` add a 2s zoom / spotlight, or a centered camera-move keyframe (`x:0.5, y:0.5, size:0.25`), at the playhead and select it. `zoomAt(x, y)` is the click-to-zoom handler passed to `Stage`: pauses, adds a full zoom (`add_zoom_full`), then sets its target to the clicked 0..1 screen point (`update_zoom` with `{ fixed: { x, y } }`) and selects it. **Render hygiene pass:** these four are now `useCallback`'d inside the hook and read the playhead off `timeMsRef` (a `useRef` mirroring `timeMs`, reassigned every render alongside `docRef`) instead of taking `timeMs` as a plain number - so their identity survives a tick, which `Stage`'s `onZoomAt` prop and `Transport`'s `onAddZoom` prop (both `React.memo`'d) need. `docRef` (bug-sweep-2 Task 8, M2) is what lets `addCameraMove` select the keyframe it actually just created - see `useTimelineActions.md`.

**`onRun()`.** Runs the AI director. `running` is checked and set to `true` SYNCHRONOUSLY, before anything is enqueued (`if (!doc || running || exporting) return; setRunning(true); ...`) - this also disables the Transport wand button (`aiRunning` prop) immediately, so a second click can't even reach the guard check, let alone enqueue a second overlapping run. The `exporting` guard (bug-sweep-2 Task 8, L3) is what actually keeps a director pass from mutating `edit.json` while the exporter renders from its own doc snapshot - belt-and-braces alongside `Transport`'s wand and `AiPanel`'s run button, which are ALSO now `disabled` on `exporting` (previously only `AiPanel`'s `running`/model-list check, and the Transport wand's `aiRunning` check, gated it - the doc comment on `brandState` below used to just assert this "can't actually happen" without anything enforcing it). The whole pass then runs inside ONE `enqueue(...)` call - a single queue task from the queue's point of view - wrapping `director.run(...)` (from `useDirector()`, `src/editor/director/useDirector.ts`), with `setRunning(false)` chained onto that call's own `.finally(...)` so `running` (and the wand's `disabled`) stays true for the task's ACTUAL full duration, not just until `enqueue` was called. `director.run` performs EXACTLY the statements the pre-Task-25 inline loop did, in the same order (`record(doc0)` once, then per step: raw `applyEditOp` + `setDoc` + `rev` bump + narration log + (for `add_zoom_full`) scrub the playhead) - it just also choreographs the fake pointer (`DirectorOverlay`, mounted below) around that sequence and returns how many steps actually landed, so `onRun`'s caller can tell a cancelled run from a completed one. Previously each step applied raw and OUTSIDE the queue, so an undo issued between two reveal steps could execute immediately and then be silently overwritten by the very next step's `setDoc` - `enqueue`-ing the whole pass closes that window: an undo/redo issued mid-run is itself queued behind it and only runs once the pass has fully settled. See `director/useDirector.md` for the choreography itself (fake-pointer moves/presses, cancel, progress) - including that hook's own render-hygiene pass (`run`/`reveal`/`aimAndPress` are now `useCallback`'d too), which is what lets `onRun` itself (below) stay stable. `onRun` is `useCallback`'d (deps `[doc, running, enqueue, director.run, folder, docRef, record, dur, setDoc, setRev]` - `director.run`, NOT the whole `director` object, which is a fresh object every render) so `Transport`'s `onAutoedit` prop and `EditorPanels`' `onRun` prop stay stable across ticks.

**`saveDocSettings` / `onAutoModel`.** From `useDocSettings(folder, docRef, setDoc, record, setRev, enqueue)` (`src/editor/hooks/useDocSettings.ts`) - `saveDocSettings` records an undo step before writing a patched `settings` object (passed to `EditorPanels` for every settings-editing panel); `onAutoModel` writes the same way but WITHOUT recording an undo step, and is passed to `AiPanel` alone for its mount-time auto-default-model effect. `enqueue` (bug-sweep-2 Task 8, M5) is the SAME queue `applyOp`/`undo`/`redo` share - a settings write used to bypass it entirely, so an in-flight `apply_edit_op` (load-mutate-save) and a settings `save_edit` (a blind full-doc overwrite) could race each other last-writer-wins on disk; now every `EditDoc` mutation goes through one serialized order. `docRef` (not a plain `doc` value - review round 1, Critical 1) is what lets `write` read the doc it's ACTUALLY landing on at execution time instead of a stale one closed over at call time - see `useDocSettings.md`.

**Media retry.** `retryMedia` (from `useEditorData`) is passed straight through to `Stage` as `onRetryMedia`, wired to `StageMedia`'s error-card Retry button.

**`brandState` (Task 39 - the living brand mark).** `!doc.settings.ui.animated_brand ? "idle" : exporting ? "exporting" : running ? "directing" : "idle"` - computed once per render and passed to `TopBar` (which forwards it, plus `pct`, straight to `TcursorMark`). The doc's OWN `ui.animated_brand` (a per-recording settings snapshot, same field family as `doc.settings.cursor.pack`) gates the state entirely off before `TcursorMark` ever sees anything but `"idle"`; `exporting` wins over `directing` if both were somehow true - `onRun`'s own `exporting` guard (above) is what actually keeps the director from running mid-export (bug-sweep-2 Task 8, L3), not just this precedence order. See `src/lib/brandWave.md` for the `MarkState` mapping and `TcursorMark.md` for the animation itself.

**Loading guard.** Renders "Loading edit..." until `doc` resolves.

**Layout.** `ResizeEdges` (frameless-window grips), `TopBar`, `EditorShell`, `moveOffDialog`, and `EditorDialogs` - the Export/Shortcuts/Settings modal stack, lifted out as one component in T34 L3 to keep this file under its line budget (`EditorDialogs.md`). Every open flag and setter still lives here, which is also what `modalOpen` is computed from; `useExportState`'s whole return is handed over as one `exportState` prop, and the `exportProject` call moved with it.

The `e-body` composition that used to sit between `TopBar` and the dialogs - `Rail`, `EditorPanels`, and a `.e-stagetoast` div wrapping `Stage`, `Toast` and `DirectorOverlay`, with `Transport` and `Timeline` pinned underneath - moved into `EditorShell` in M1a. `.e-stagetoast` itself survives verbatim inside `StageSlot`, so the undo/redo pill and the director's scrim still anchor to the stage rather than the window (Task 11, ux audit #17).

**The `shell` bundle.** Everything the four editor types need reaches `EditorShell` as one `ShellProps` object (`shell/slotProps.md`), built from this file's own locals as a shorthand literal. That is what let `Editor.tsx` drop back under the 200-line cap while gaining a whole layout subsystem: the ~45 lines of JSX attributes it used to spend placing five components became ~12 lines of object literal, and `EditorSlot` spreads them back out.

### Render hygiene (sweep2 T3)

`Timeline`, `Transport`, `EditorPanels`, and `Stage` are now `React.memo`'d (see each one's own doc), so `Editor`'s own per-tick re-render (`setTimeMs`, ~16-60/sec during playback or a scrub) no longer automatically cascades into re-rendering all of them and everything below them. For that memo to actually hold across a tick - not just exist - every prop `Editor` hands them has to be reference-stable across a tick too, which is what most of the callback work above is actually for:

- **`useEditorCallbacks(...)`** (`src/editor/hooks/useEditorCallbacks.ts`) - a new hook, split out of `Editor.tsx` purely to stay under this file's line budget, that builds `onTime`/`aimAt`/`onMoveMode`/`onSeek`/`onPlayToggle`/`onAspect`/`cycleQuality`/`onMuteToggle` with `useCallback`. `applyOp` itself stays here (several other hooks need it built first) and is passed in.
- **`timeMsRef` / `trimRangeRef`** - two more `useRef`s reassigned every render alongside `docRef`, so any callback that needs the CURRENT playhead/trim (`onTime`, `onPlayToggle`, and - via `useTrimActions`/`useTimelineActions` - the trim/add-region actions) can read it at call time without needing `timeMs`/`trimRange` themselves in a `useCallback` dependency array, where they'd force a new function every tick.
- **One shared `onSeek`.** `Transport`'s skip buttons and `Timeline`'s track-body scrub/drop used to each own an identical inline `(ms) => { setPlaying(false); setTimeMs(ms); }` - now built once in `useEditorCallbacks` and passed to both, and (sweep-2 gate finding) also threaded to `EditorPanels` -> `ZoomInspector`, so changing a zoom-scoped control outside its span can jump the playhead into it (`ZoomInspector.md`'s `zoomScopedSeekMs`).
- **`hasWebcamSignal(layout)`** (`hooks/editorData.ts`) passed to `Timeline` as `hasWebcam`, threaded to `CameraLane` - gates its empty-lane hint off for a recording with no webcam (see `CameraLane.md`).
- **`EditorPanels`' gated `timeMs`.** Only `CameraPanel` (`tab === "camera"`) needs a LIVE playhead; every other panel doesn't touch it at all. `ClassicShell` passes `timeMs={p.tab === "camera" ? p.timeMs : 0}` - a constant `0` (not the ticking value) whenever the active view doesn't need it, so `EditorPanels`' memo comparison sees no change on a tick unless the Camera panel is actually showing. The two places that still need the TRUE current time regardless of tab read `timeMsRef` instead, which never defeats memo on its own since a ref's identity never changes: `EffectsPanel`'s "add layout segment at the playhead" button, and `LayoutsPanel`, which reads it once on mount to open on the layout the playhead is inside.
- **`useMoveModeGuard`, `useTrimActions`, `useTimelineActions`, `useDirector`** were all touched too (each is `useCallback`'d now, with `useTrimActions`/`useTimelineActions` taking `timeMsRef` instead of `timeMs`) - see their own docs. Without this, a callback built by any of THEM would have been fresh every render regardless of anything done here, quietly defeating the whole pass through one weak link.

### Notes

- `quality` cycles 480→720→1080 and re-runs the proxy effect (initialized to `DEFAULT_PROXY_HEIGHT`, the same 720 `preprocess_project` transcodes ahead of time); `muted` toggles the preview `<audio>`.
- `proj` is the last path segment of `folder`, shown by `TopBar`.
- `showExportDialog` is the only export-dialog state `Editor` owns itself; `exporting`/`pct`/`exportDone`/`exportError` are all lifted from `useExportState` (Task 11 - previously `useEditorData`) and reach `ExportDialog` through `EditorDialogs`.
- `showShortcuts` is the analogous local state for `ShortcutsOverlay` - toggled by `useEditorKeymap`'s `onOverlay` callback (fires when `resolveKeyAction` returns `"overlay"`, i.e. the `?` key) and cleared by the overlay's own `onClose` (scrim click or Escape).
- `showSettings` (Task 35) is the analogous local state for `EditorSettingsDialog` - toggled by `TopBar`'s gear button (`onOpenSettings`) and cleared by the dialog's own `onClose` (scrim click or Escape), same shape as `showExportDialog`/`showShortcuts`.
- `toast` / `onSwap` / `pushToast` / `dismissToast` come from `useUndoToast()` (`src/editor/shell/Toast.tsx`); `onSwap` is handed to `useEditHistory` and fires once per actual undo/redo swap (keyboard or button), and `pushToast` (Task 11) is handed to `useExportState` as its `onExportWarning` handler.
- **`modalOpen` (bug-sweep-2 Task 8, M4; extended in review round 1, Important C).** `showExportDialog || showShortcuts || showSettings || moveOffOpen || running` (`moveOffOpen` is `useMoveModeGuard`'s own `pending` state, re-exposed alongside `moveOffDialog` so `Editor` can fold it into this check; `running` is the AI director's own state - its scrim, `DirectorScrim`, is its own kind of modal), passed to `useEditorKeymap` alongside a separate `shortcutsOpen: showShortcuts`. Every global shortcut (Space/Z/S/Delete/`?`) is inert while ANY of these five is open - previously only typing in a text field was checked, so e.g. `z` typed while the Export dialog was open silently added a zoom behind it, and a director run behind the same window would have let one through too. `shortcutsOpen` is passed SEPARATELY (not just folded into `modalOpen`) so `?` can still toggle `ShortcutsOverlay` CLOSED while it, specifically, is the open modal - see `useEditorKeymap.md`/`keymap.md`'s `resolveKeyAction`. Since M1a A3 the same boolean also goes into the `shell` bundle (`ShellProps.modalOpen`): the editor shell owns one key of its own, `Ctrl+Space` to maximize an area, and it has to go inert behind a dialog for exactly the same reason every other shortcut does.

`useSilences(folder, docRef, applyOp, pushToast)` provides `onDetectSilences` for the transport's Remove silences: one scan, one `add_cuts`, one toast.
