# src/editor/Editor.tsx

The post-record editor's component: the view state (playhead, selection, tab, range, aim, volume), the mode guards, and the composition of `TopBar`, `ClassicShell` and the modal stack. The document side of the editor - the doc itself, its fetches, the op queue, the history, the clock, the export run - is one call to [useEditorSession](hooks/doc/useEditorSession.md); the callbacks handed to the memoized hot tree are [useEditorCallbacks](hooks/input/useEditorCallbacks.md); which modal is open is [useEditorModals](hooks/input/useEditorModals.md); and the map from all of those onto the shell's contract is [buildShellProps](model/shellProps.md). It no longer places `Stage`, `Transport`, `Timeline` or the panels itself: which of them are on screen, and where, is the active workspace's business. The preview plays the recording natively (`Stage`) and applies the exact camera curve (`cameraTrack`) as a transform, so it is smooth 60fps; edits go through the Edit API and `rev` bumps so the camera curve refetches.

## Editor

**`tab` (2026-09-14).** `useState<Tab | null>(() => readPanelTab(TAB_IDS))`, with one `useEffect` on `[tab]` calling `writePanelTab(tab)`. `null` is "the panel column is collapsed" - a real resting state since the column became collapsible (`shell/panelState.md`), reached by pressing the open rail tab again or by any panel's close X. It is seeded from and written back to `localStorage` (`tcursor.editor.panel`), so the editor reopens the way it was left, collapsed included; storage that throws or holds a value from another build reads as `"ai"`, never as a collapsed editor the user did not ask for. The effect is the only writer, so every path that changes the tab persists without having to remember to.

**`range` (time remap T7).** `useState<[number, number] | null>(null)` - the ruler's Shift+drag selection in clip ms, held here for the same reason `sel` is: the TIMELINE edits and draws it (`timeline/useRangeSelect.ts`, `RangeOverlay`) while the TRANSPORT acts on it (`TransportTools`' Cut and Speed 2x) and clears it afterwards, and neither area owns the other. `Editor` never reads it - it only declares it and passes `range`/`setRange` down in the bundle.

```tsx
export function Editor({ folder, onClose }: { folder: string; onClose: () => void }): JSX.Element
```

Renders the editor layout and manages the editing lifecycle for one recording.

### Props

- `folder: string` - absolute path to the project directory. *Why:* every IPC call (load, preview tracks, autoedit, export) takes the folder as its key.
- `onClose: () => void` - return to the HUD. *Why:* the editor does not own the window/view switch; the parent does.

### Behavior

**Theme (light / dark / system).** `Editor` renders the `.editor` root that `editor.css` hangs both palettes off, so the editor follows the same Preferences theme setting the recorder HUD does. `applyTheme` (`src/hud/preferences/applyTheme.ts`) stamps `data-theme="light"|"dark"` on the document root - the HUD and the editor share one window, so the attribute is already set by the time `Editor` mounts from the HUD. The dark palette is the plain `.editor` rule (the default, unchanged from before the light theme existed) and the light one is `:root[data-theme="light"] .editor`, repeated under `@media (prefers-color-scheme: light)` guarded by `:root:not([data-theme="dark"])`. That media copy is what covers the first paint of a cold start into a project (`getLaunchProject` routes straight past the HUD); since 2026-09-14 `App`'s own startup effect then applies the stored theme (`getSettings` then `applyTheme`), so an "always light"/"always dark" preference holds from the first settings read even when the HUD never mounts. The light palette was darkened on the same day after the owner found it too pale to read: the ground steps down to `#e6e7eb`, hairlines and dividers double, and every text rung (including `--e-dim`, which used to be the one grey shared with the dark theme) is a darker grey. `themeTokens.test.ts` fails the build if a token is declared in one palette and not the other, or if any editor stylesheet grows a raw hex colour outside the palette blocks.

**Playback.** Driven by the native `<video>` in `Stage`, which reports its time via `onTime`; `onTime` (built in `useEditorCallbacks`, see "Render hygiene" below) sets `timeMs` and stops playback at the trim's resolved out point - not just the clip end - so play never runs into a trimmed-out tail. At the boundary it parks `timeMs` *exactly* on `outMs` (not the frame or two of overshoot the video reports before the pause lands), so the playhead sits on the line rather than past it. There is no RAF playhead loop in the editor. `dur` is the `<video>`'s real duration (`vidDurMs`) when known, else `doc.trim.out_ms` - the encoded length can differ from the seeded timeline span, so the video's own duration is the source of truth for the playhead end. Scrubbing the timeline itself is unrestricted (only `onPlay`, below, respects the trim start).

**Trim + aspect (passed to `Transport`; also still passed to `Stage`, which ignores them since the look pass retired `StageToolbar` - see `stage/Stage.md`).** `trimRange = resolveTrim(doc?.trim ?? {in_ms:0,out_ms:0}, dur)` is computed once per render (mirrored into `trimRangeRef`, read by `useEditorCallbacks` - see "Render hygiene") and `trimmed = trimRange.inMs > 0 || trimRange.outMs < dur` is derived from it after the loading guard. `onPlayToggle` (built in `useEditorCallbacks`, passed to `Transport` as `onPlay`) snaps `timeMs` to `trimRange.inMs` first when starting playback from outside `[inMs, outMs)`. `doc.aspect`/`SetAspect` are passed straight through as `aspect`/`onAspect` (`onAspect` also from `useEditorCallbacks`) to BOTH `Transport` and `Stage` (`Stage` also gets `aspectLocked={exporting || dur <= 0}`, computed inline the same way `Transport`'s own `locked` is; it no longer reads either, the aspect chip in `Transport` being the editor's one aspect control now). The actual trim RANGE is set by dragging `TrimOverlay`'s edge handles on the `Timeline`, not from `Transport`. `exporting` (from `useExportState`) is also passed through as `Transport`'s `exporting` prop (Task 36) - `Transport` locks its play/trim/aspect controls, AND (bug-sweep-2 Task 8, L3) its AI-director wand, while an export is running, so nothing changes underfoot mid-render. `exporting` is likewise now passed to `EditorPanels` (→ `AiPanel`'s run button) for the same reason.

**`onTab` is gone (M1a).** It used to be `useCallback((t: Tab) => { if (t !== tab) { setSel(null); setAimOn(false); } setTab(t); }, [tab])` - one shared navigation handler for `Rail` and the since-removed `StageToolbar` that cleared the selection on every tab switch. The clearing half of that is now wrong: selection is an independent axis, so changing a panel tab must leave `sel` alone. `Editor` therefore passes plain `tab`/`setTab` down in the `SlotProps` bundle, and the shell builds the one handler the rail needs (`onTab`). Since the classic rail came back it draws the eight tabs itself (`shell/PanelTabs.md`), and since the column became collapsible `ClassicShell`'s `onTab` resolves a press through `nextTab` (`shell/panelState.md`) rather than setting the tab outright.

**Esc deselects.** `keyAction` (`model/keymap.md`) gained a `"deselect"` action for Escape, fired only when something IS selected. `useEditorKeymap` takes a new `escOwned` flag, which `Editor` passes as `arrangeOn`: stage arrange mode owns Escape for its own exit and deliberately KEEPS the segment selected so the pill and the inspector button can re-enter, so Escape stays that surface's key while it is live.

**Zoom aiming (`aimOn` / `aimPoint` / `aimMode` / `aimAt` / `onMoveMode`).** A Region-target zoom (`ZoomTarget::Fixed`) stores a 0..1 screen-content aim point, and `Stage` can place it directly on the preview. `aimPoint` = `useMemo(() => zoomTargetPoint(selZoom?.target), [selZoom])` (`selZoom = doc?.zooms.find(z => z.id === sel)`) - `null` unless a Region zoom is selected, which makes it double as "is aiming even possible right now". Memoized (render hygiene pass) because `zoomTargetPoint` returns a fresh `[x, y]` array literal every call - without the `useMemo`, `aimPoint` would be a new array reference every render even when the underlying target hadn't changed, defeating `Stage`'s memo on every tick since `aimPoint` is one of its props. `aimMode` = `aimOn && !moveMode && !arrangeOn && !!aimPoint`.

**Stage arrange mode (T34 L3, `arrangeSeg` / `arrangeOn` / `onArrange`).** `useArrangeMode(doc, sel)` (`hooks/input/useArrangeMode.md`) owns the third exclusive stage mode: selecting a layout PILL enters it, Escape leaves it while remembering the segment, `onArrange` (`LayoutInspector`'s "Arrange on stage" button) re-enters, and deselecting exits outright. `arrangeSeg` goes to `Stage` (non-null IS the mode, and it is only ever a segment that still exists); `arrangeOn` + `onArrange` go to `EditorPanels` for the inspector, and `arrangeOn` is folded into `aimMode` above for the same reason `!moveMode` is - the three modes all claim the same canvas pointer. `Editor` also passes `applyOp` down to `Stage` for the first time, used only by arrange mode's commit-on-release. The hook is built AFTER `useEditorCallbacks` because it needs `onSeek` (it seeks into the segment on entry - see `arrangeMode.md`'s `arrangeSeekMs`), and it returns the `onSel` that `Timeline` now gets in place of a bare `setSel`, so a pill re-click is a real entry gesture rather than a no-op set.

The `!moveMode` term is the mutual-exclusion rule the two stage gestures need: camera Move mode and zoom aiming both claim the same pointer on the same canvas. It is deliberately a **suppression**, not a cancellation - turning Move mode on (`onMoveMode`, built in `useEditorCallbacks`, wrapping `requestMoveMode`) clears `aimOn` outright, but Move mode being on merely hides aiming, so nothing here can trigger `useMoveModeGuard`'s destructive "turn Move off and delete your keyframes" dialog as a side effect of wanting to aim a zoom. `ZoomInspector` disables its Aim button in that state and says why. Switching the rail tab also clears `aimOn`, since it clears the selection.

`aimAt(x, y)` (built in `useEditorCallbacks`) is the commit: a plain `update_zoom { target: { fixed: { x, y } } }` through `applyOp`. **Render hygiene pass:** a reticle drag no longer calls `aimAt` on every pointermove - `Stage` now debounces that call (trailing ~80ms, flushed on release) and drives the reticle's on-screen position from its own local optimistic state instead, exactly like `Slider.tsx` debounces its `onChange` commit (see `Stage.md`'s "Reticle drag debounce"). `useEditHistory`'s `COALESCE_MS` window still folds the resulting burst of `update_zoom`s into one undo step either way - no new undo machinery.

**`addZoom` / `addSpotlight` / `addCameraMove` / `zoomAt`.** From `useTimelineActions(applyOp, timeMsRef, docRef, setSel, setPlaying)` (`src/editor/hooks/doc/useTimelineActions.ts`, Task 36 - kept out of `Editor` so it stays under the line limit, mirroring `useTrimActions`). `addZoom`/`addSpotlight`/`addCameraMove` add a 2s zoom / spotlight, or a centered camera-move keyframe (`x:0.5, y:0.5, size:0.25`), at the playhead and select it. `zoomAt(x, y)` is the click-to-zoom handler passed to `Stage`: pauses, adds a full zoom (`add_zoom_full`), then sets its target to the clicked 0..1 screen point (`update_zoom` with `{ fixed: { x, y } }`) and selects it. **Render hygiene pass:** these four are now `useCallback`'d inside the hook and read the playhead off `timeMsRef` (a `useRef` mirroring `timeMs`, reassigned every render alongside `docRef`) instead of taking `timeMs` as a plain number - so their identity survives a tick, which `Stage`'s `onZoomAt` prop and `Transport`'s `onAddZoom` prop (both `React.memo`'d) need. `docRef` (bug-sweep-2 Task 8, M2) is what lets `addCameraMove` select the keyframe it actually just created - see `useTimelineActions.md`.

**The AI Director (M4 T5).** `const ai = useAiRun({ folder, docRef, dur, enqueue, record, setDoc, bumpRev, onSeek, setPlaying })` (`director/useAiRun.md`) owns the whole client side: the propose pass, the review sheet's state (the run, the skipped ids, the previewed id, the stage outline) and its handlers, the one-undo-step apply, and the optional pointer replay. Its fields spread into `ShellProps` as `running` (`ai.running`: thinking, applying or replaying), `aiError`, `aiRun` / `aiSkipped` / `aiApplying` / `aiPreviewId` / `stageOutline`, `aiProgress` / `aiPlanning` / `pointerRef` / `onCancelRun`, and the handlers `onToggleItem` / `onPreviewItem` / `onApplyRun` / `onDiscardRun`. The hook reads its inputs through a ref at call time, so every handler keeps one identity across ticks without `Editor` juggling deps; `bumpRev` is a fresh arrow each render for the same reason it can be: nothing depends on its identity.

**`onRun()`.** `useCallback(() => { if (!exporting) void ai.run(); }, [exporting, ai.run])`. The `exporting` guard (bug-sweep-2 Task 8, L3) is what keeps a director pass from mutating `edit.json` while the exporter renders from its own doc snapshot - belt-and-braces alongside `Transport`'s wand and `AiPanel`'s run button, which are also `disabled` on `exporting`. Re-entry is the hook's own business (a synchronous `busyRef`), so `running` is not a dep here and the callback stays stable for `Transport`'s `onAutoedit` prop and `EditorPanels`' `onRun` prop. Only the apply holds the op queue: the propose fetch mutates nothing, so the user can keep editing while the model thinks, and the apply runs inside ONE `enqueue(...)` so an undo issued mid-apply queues behind it instead of racing it (the same reason the old one-shot reveal was enqueued whole). The one-shot flow's live narration log is gone: the sheet says what will be done before it is done.

**Media retry.** `retryMedia` (from `useEditorData`) is passed straight through to `Stage` as `onRetryMedia`, wired to `StageMedia`'s error-card Retry button.

**`brandState` (Task 39 - the living brand mark).** `!doc.settings.ui.animated_brand ? "idle" : exporting ? "exporting" : running ? "directing" : "idle"` - computed once per render and passed to `TopBar` (which forwards it, plus `pct`, straight to `TcursorMark`). The doc's OWN `ui.animated_brand` (a per-recording settings snapshot, same field family as `doc.settings.cursor.pack`) gates the state entirely off before `TcursorMark` ever sees anything but `"idle"`; `exporting` wins over `directing` if both were somehow true - `onRun`'s own `exporting` guard (above) is what actually keeps the director from running mid-export (bug-sweep-2 Task 8, L3), not just this precedence order. See `src/shared/brand/brandWave.md` for the `MarkState` mapping and `TcursorMark.md` for the animation itself.

**Loading guard.** Renders "Loading edit..." until `doc` resolves.

**Layout.** `ResizeEdges` (frameless-window grips), `TopBar`, `EditorShell`, `moveOffDialog`, and `EditorDialogs` - the Export/Shortcuts/Settings modal stack, which since M3 also receives `onApplyMotion` (`() => void applyOp({ op: "apply_motion_default" })`, Settings > Motion's "Apply to all regions" - a doc edit, so it goes through `applyOp` and undoes as one step, unlike the settings writes that go through `saveDocSettings`), lifted out as one component in T34 L3 to keep this file under its line budget (`EditorDialogs.md`). Every open flag and setter still lives here, which is also what `modalOpen` is computed from; `useExportState`'s whole return is handed over as one `exportState` prop, and the `exportProject` call moved with it.

The `e-body` composition that used to sit between `TopBar` and the dialogs - `Rail`, `EditorPanels`, and a `.e-stagetoast` div wrapping `Stage`, `Toast` and `DirectorOverlay`, with `Transport` and `Timeline` pinned underneath - moved into `EditorShell` in M1a. `.e-stagetoast` itself survives verbatim inside `StageSlot`, so the undo/redo pill and the director's scrim still anchor to the stage rather than the window (Task 11, ux audit #17).

### Render hygiene (sweep2 T3)

`Timeline`, `Transport`, `EditorPanels`, and `Stage` are now `React.memo`'d (see each one's own doc), so `Editor`'s own per-tick re-render (`setTimeMs`, ~16-60/sec during playback or a scrub) no longer automatically cascades into re-rendering all of them and everything below them. For that memo to actually hold across a tick - not just exist - every prop `Editor` hands them has to be reference-stable across a tick too, which is what most of the callback work above is actually for:

- **`useEditorCallbacks(...)`** (`hooks/input/useEditorCallbacks.md`) - a hook that builds `onTime`/`aimAt`/`onMoveMode`/`onSeek`/`onPlayToggle`/`onAspect`/`cycleQuality`/`onMuteToggle` with `useCallback`. `applyOp` comes from `useEditorSession` (several other hooks need it built first) and is passed in.
- **`timeMsRef` / `trimRangeRef`** - two more `useRef`s reassigned every render alongside `docRef`, so any callback that needs the CURRENT playhead/trim (`onTime`, `onPlayToggle`, and - via `useTrimActions`/`useTimelineActions` - the trim/add-region actions) can read it at call time without needing `timeMs`/`trimRange` themselves in a `useCallback` dependency array, where they'd force a new function every tick.
- **One shared `onSeek`.** `Transport`'s skip buttons and `Timeline`'s track-body scrub/drop used to each own an identical inline `(ms) => { setPlaying(false); setTimeMs(ms); }` - now built once in `useEditorCallbacks` and passed to both, and (sweep-2 gate finding) also threaded to `EditorPanels` -> `ZoomInspector`, so changing a zoom-scoped control outside its span can jump the playhead into it (`ZoomInspector.md`'s `zoomScopedSeekMs`).
- **`hasWebcamSignal(layout)`** (`model/editorData.ts`) passed to `Timeline` as `hasWebcam`, threaded to `CameraLane` - gates its empty-lane hint off for a recording with no webcam (see `CameraLane.md`).
- **`EditorPanels`' gated `timeMs`.** Only `CameraPanel` (`tab === "camera"`) needs a LIVE playhead; every other panel doesn't touch it at all. `ClassicShell` passes `timeMs={p.tab === "camera" ? p.timeMs : 0}` - a constant `0` (not the ticking value) whenever the active view doesn't need it, so `EditorPanels`' memo comparison sees no change on a tick unless the Camera panel is actually showing. The two places that still need the TRUE current time regardless of tab read `timeMsRef` instead, which never defeats memo on its own since a ref's identity never changes: `EffectsPanel`'s "add layout segment at the playhead" button, and `LayoutsPanel`, which reads it once on mount to open on the layout the playhead is inside.
- **`useMoveModeGuard`, `useTrimActions`, `useTimelineActions`, `useAiRun`** were all touched too (each is `useCallback`'d now, with `useTrimActions`/`useTimelineActions` taking `timeMsRef` instead of `timeMs`) - see their own docs. Without this, a callback built by any of THEM would have been fresh every render regardless of anything done here, quietly defeating the whole pass through one weak link.

### Notes

- `quality` cycles 480→720→1080 and re-runs the proxy effect (initialized to `DEFAULT_PROXY_HEIGHT`, the same 720 `preprocess_project` transcodes ahead of time); `muted` toggles the preview `<audio>`.
- `proj` is the last path segment of `folder`, shown by `TopBar`.

`useSilences(folder, docRef, applyOp, pushToast)` provides `onDetectSilences` for the transport's Remove silences: one scan, one `add_cuts`, one toast.

**Classic layout (2026-09-13).** `EditorShell` is gone; `ClassicShell` renders the rail, the panel slot, the stage, the right properties sidebar, the transport and the timeline from the same `ShellProps` bundle. The area/workspace shell is archived on `archive/m1a-shell`.

**Density (laptop pass, 2026-09-15).** `useDensityVars()` is called at the top of the component and its result is the `style` on the `.editor` element - in BOTH return paths, the loading one included, so the loading state is never typeset at a different scale than the editor that replaces it. That style is the only place the density ladder enters CSS: a `--e-density` multiplier that every `--e-text-*`, `--e-sp-*`, radius and `--e-ctl-*` rung in `editor.css` is a `calc()` of, plus the stepped column and lane sizes. `Editor` neither computes nor reads any of it - see `shell/density.md` for the model and `shell/useDensity.md` for the store. It is deliberately NOT part of `ShellProps`: it is a viewport fact, not document state, and the two components that also need the numbers (`ClassicShell`, `Timeline`) read the same store directly.

**Theme and accent effect (2026-09-15).** `useEffect(() => applyProjectUi(doc.settings.ui), [doc.settings.ui])` stamps the project's theme and accent on the document root on mount and after every doc change (`applyUi.md`), so Project Settings > Interface is visible at once and survives undo.
