# src/hud/Hud.tsx

Root component of the floating recorder bar. Owns device selection and the capture toggles directly; delegates the record/stop/preprocess lifecycle to `useRecordingFlow`, the export-event flags to `useExportProgress`, the persisted theme to `useHudTheme`, and the menu/sheet/sources/panel state to `useHudChrome`. Wires together every visual region: the idle card (`IdleCard`: header, webcam preview, source rows, toggles, Record), the take pill (`TakeBar`) while recording or saving, and the Settings and Preferences panels, which are sheets inside the idle card's own body. This is the single stateful hub; all child components are controlled.

## Hud

Renders the full HUD window content and manages the recording lifecycle.

### Props

- `onEdit?: (folder: string) => Promise<void>` - optional callback invoked after `stopRecording` succeeds, with the project folder path. *Why:* the stop path no longer automatically kicks off the export pipeline; instead it hands the folder to the caller (`App`) so it can open the editor. When `onEdit` is not provided the recorder operates in standalone mode and the export is not triggered. NOT called by a graceful close (`handleClose`) - see below. *Why a `Promise` (fix round 1, item 2, controller ruling 2026-09-02):* `useRecordingFlow`'s `finish` awaits it (via `handOff`, `docs/api/src/hud/hooks/useRecordingFlow.md`) before deciding whether to reset `saving` - `App.tsx`'s `openEditor` (the real `onEdit`) does its own async window resize before switching views, and `finish` must not let its own saving-reset `setSize` race that.

### Behavior

**Window sizes.** Every size the window ever takes comes from `useHudWindowSize` (`src/hud/hooks/useHudWindowSize.ts`, the single source of truth, since that hook is also the one calling `win.setSize`); this component only imports `takeWidth`, to pin the `.hud` surface while the pill is shown. Opening Settings or Preferences no longer touches the window at all (owner, 2026-09-14: "we need to do it like how we are handling display changes") - the panel is a sheet inside the card's body, so the card, the window and the header all stay exactly where they are. The old bar-to-box morph (`BOX_W`/`BOX_H`, `openPanel`'s `morphWindow`, `restoreBar`, the `.as-box` class and the `barShown` gate) is gone with it; `morphWindow` itself remains, for the bar-to-pill glide inside the hook.

**State and hooks.**
- `displays / mics / sel / setSel` - enumerated devices and current selection from `useDevices`, which polls `listDisplays` and `listAudioInputs` via IPC on mount AND re-polls on every `devicechange` (task-6 (d)). *Why a hook:* keeps enumeration and refresh logic out of this file.
- `camId` - selected camera device id, or `null` to mean "first available". *Why nullable:* the browser does not guarantee a stable device id across sessions.
- `camOn` - whether the camera preview and recording are active. *Why separate from camId:* lets the user keep a camera selected but temporarily disabled without losing the selection.
- `camStreamRef` - a ref holding `cam.stream` (below), threaded into `useRecordingFlow` as `camStream: () => camStreamRef.current()`. *Why a ref instead of passing `cam.stream` directly:* `cam`'s own `enabled` argument (below) needs `saving`, which only exists once `useRecordingFlow` has already returned - declaring `cam` before `useRecordingFlow` (the old order) would make `saving` unavailable, but declaring `useRecordingFlow` first needs `cam.stream` before `cam` exists. The ref breaks that circularity: `useRecordingFlow` gets a stable wrapper function up front, and `cam`'s own declaration (right after) points `camStreamRef.current` at the real getter - by the time anything actually CALLS it (`webcam.start`, at record-start), it's already live.
- `recording / paused / saving / savePct / err / toggle / togglePause / stopForClose` - from `useRecordingFlow` (see `docs/api/src/hud/hooks/useRecordingFlow.md`), which owns the whole record -> stop -> preprocess -> edit lifecycle. `stopForClose` is the graceful stop `handleClose` (below) runs before the window actually closes. `exporting`/`pct` (below) stay local to `Hud` - they are unrelated leftover state from before export moved into the editor's `ExportDialog` (see `src/editor/Editor.tsx`); nothing in the current app flow sets `exporting` true from the HUD.
- `cam` - live preview handle from `useWebcamPreview(camId, camOn && !saving)`. Exposes `cam.ref` (bound to the `<video>` element), `cam.on` (whether a stream is active - now also flips back to `false` on a live track ending, and self-recovers on `devicechange` once the device reappears, task-6 (b)/M4), and `cam.stream()` (the `MediaStream` for the recorder). The `&& !saving` (item 4, user-reported 2026-09-02) releases the stream - and turns the camera LED off - the instant Stop's finalize begins, the same as if the user had toggled the camera off; it re-acquires automatically once `saving` goes back to `false`, since that's the same `enabled` gate `useWebcamPreview` already re-runs on. `saving`'s promisified `onEdit` handoff (fix round 1, item 2, see `useRecordingFlow.md`'s `handOff`) means this re-acquire never actually fires on the normal Stop-into-editor path any more, either: `saving` now stays `true` the whole time `Hud` is still mounted after a successful Stop (it only resets on a FAILED handoff, or when there's no `onEdit` at all), so `camOn && !saving` never flips back to `true` before `Hud` unmounts - the brief camera-preview flicker that fix used to cause during the handoff window is gone.
- `cameras` - list of detected camera devices from `useCameraDevices`. Re-enumerates when `cam.on` flips (the numeric argument forces a re-query tick). *Why on `cam.on`:* browsers only expose camera labels after permission is granted, which happens the moment the preview starts.
- `exporting` / `pct` / `exportErr` - from `useExportProgress(lastFolder)` (see its own doc), which owns the three `export-*` Tauri listeners. Nothing in the current app flow sets `exporting` true from the HUD; `exportErr` renders in the same titlebar slot as `err`.
- `panel` - which panel has the idle card's body: `"settings"`, `"preferences"`, or `null`, from `useHudChrome`. Handed to `IdleCard` alongside `panelBody` (the built `<Settings>` or `<Preferences>` element), where it is the `AnimatePresence` key, so a panel arriving, leaving or being swapped for the other one rides the card's own frost - the same flip the display picker uses.
- `takeShown` - `true` once the take pill is the SHOWN state (the idle bar has frosted out), `false` once the bar is; set by `StateSwap`'s `onSettled`. It, not `recording`, drives `useHudWindowSize`'s mode, the `.hud` root's `as-take` class (the pill rounding and the inline `width: takeWidth(pill)` pin, `pill` being `{ cam: camOn, meter: micOn || sysOn, warn: warn != null, sources: sourcesOpen }`, the sources this take shows). The root also takes `has-sources` while the sheet is open, which un-rounds the 31px pill into a 22px panel around the pill and the sheet together, so the window is sized for what is on screen rather than for what the flow just switched to.
- `chrome.sheet` - whether the idle card's body is flipped to the "what to record" sheet (`TargetSheet`, via `IdleCard`); set from the card's screen row and cleared by a pick or Back, and the same flag the take pill's Sources sheet uses for its own display list - the two surfaces are never on screen together, so one flag (and one `menu` id slot) serves both.
- `chrome.sources` - whether the take pill's Sources sheet (`SourcesSheet`) is open, toggled by the pill's Sources button. `sourcesOpen = chrome.sources && !saving` is what actually renders and what goes into `pill.sources`: there is no take left to switch anything on once Saving starts. `useHudChrome`'s `!recording` effect clears `sources`, `menu`, `sheet` and `panel` the moment a take ends, so the idle card never comes back mid-flip or with a stale menu hanging off it.
- `src` - `useSourceSwitch` (see its own doc): the three mid-take switch handlers plus their own `err`. `warn = err ?? src.err` is the single message the take pill shows, so a failed switch surfaces exactly where a failed recorder already does. `src.clearErr()` runs when the Sources button is pressed, so a stale failure does not outlive the sheet that caused it.
- `lastFolder` ref - stores the project folder path returned by `stopRecording` so the export-error listener can call `revealItemInDir` even after recording state has reset.
- `onUi` - the one value `useHudTheme()` returns: the callback `Preferences` calls when the user changes theme or accent. The ref that keeps the `matchMedia` handler off stale state lives inside that hook now.
- `elapsed` - elapsed recording time from `useRecordingTimer(recording, paused)`.
- `audio` - `{ read, live }` from `useAudioLevels(recording && !paused && (micOn || sysOn))` (see `docs/api/src/hud/hooks/useAudioLevels.md`). Levels come from the Rust capture that is writing the WAV, so the meter shows the take itself and the webview never opens the microphone a second time (this replaced `useMicWaveform`, which did). *Why the toggles are folded into the hook's `on` argument, not just its rendering:* a source the user has toggled off produces no reports at all, which is what makes "the meter is flat" honest rather than a display choice (task-6 (c), user-reported finding H2 - the HUD used to show a live-looking waveform even when muted). `read` and `live` are passed straight into `TakeBar`, which hands them to its level slot (`RecMeter`).

**Window sizing (`useHudWindowSize(menu, takeShown ? (saving ? "saving" : "recording") : "idle", pill)`).**
Extracted hook (`src/hud/hooks/useHudWindowSize.ts`, see its own doc) that resizes the OS window to fit the bar's current content - taller while a dropdown is open so the menu list overflows into extra window space rather than being clipped by the frame, content-fit around the take pill (`TAKE_WIDTH` by `TAKE_HEIGHT`, gliding there about the window's horizontal centre once the idle bar has frosted out) while recording or saving (D5 / item 3, user-reported 2026-09-02 - the window used to stay at the old bar's idle width around the much narrower recording content, and separately fell BACK to that same width around ~300px of saving-bar content since `mode` never distinguished "saving" from "idle" before) - and fixes the cold-launch centering bug (L1): the window boots at `tauri.conf.json`'s 860px width, and the hook's first resize to the real 360px card would otherwise leave it off screen centre, since `setSize` keeps the top-left corner fixed. It takes no `barShown` gate any more: nothing else owns the window's size, since the panels open inside the card.

**Theme.** `useHudTheme()` - see its own doc. (`ui.animated_brand`, Task 39's feel knob, is no longer read: the idle bar's mark is always at rest and the take pill has no mark - its recording tell is the clock's breathing dot. The editor's top-bar mark still honours the knob.)

**`handleClose()` (task-6 (a) / ruling R6).** `await stopForClose(); win.close();` - awaits the graceful stop (a no-op that resolves immediately if nothing is recording, so this is still a single click in the common case) before actually closing the window, so a recording in progress is finalized and saved instead of the process just dying mid-take (the Critical finding this task starts from). This is the React-side half of the fix; `src-tauri/src/lib.rs`'s `on_window_event` `CloseRequested` guard is the Rust-side backstop that holds even if this function never runs at all (OS close button, Alt+F4, a wedged renderer).

**Export events.** `useExportProgress(lastFolder)` - see its own doc for the three listeners and what each one reveals.

**`toggle()` / `togglePause()` / `stopForClose()`.**
All three come straight from `useRecordingFlow(...)`, fed `micOn`/`sel.micId`/`sel.displayId`/`sysOn`/`gameMode`/`camOn`/`() => camStreamRef.current()` (see `camStreamRef` above)/`webcam`/`onEdit`/`lastFolder`. See `docs/api/src/hud/hooks/useRecordingFlow.md` for the full record -> stop -> preprocess -> edit sequence, the record-button re-entrancy guard, and the graceful-close variant. `lastFolder` itself stays a `Hud`-owned ref (passed into the hook by reference) purely so the unrelated export-error listener above can still read it.

**`openExistingProject()`.**
Calls `openProject()` (native `*.tcursor` file picker) and, on success, `await`s `onEdit?.(folder)` with the returned containing folder - the same prop `toggle()`'s stop path uses, so opening an existing project routes to the editor identically to finishing a fresh recording. Awaited (not fire-and-forget) now that `onEdit` is promisified (fix round 1, item 2) so a rejection lands in the same `catch` as a cancelled dialog rather than becoming an unhandled promise rejection - there is nothing to surface either way.

**Panel, menu and sheet helpers.** `chrome.openPanel` / `closePanel` / `toggleMenu` / `closeMenu` / `picked` / `openSources`, plus the Escape listener and the end-of-take reset, all come from `useHudChrome(recording)` - see its own doc.

**Rendered regions.**
- `panelBody` - the built `<Settings onClose={closePanel} />` or `<Preferences onClose={closePanel} onUiChange={...} />` (its `onUiChange`, Task 39 - see `Preferences.md` - updates `themeRef` and calls `applyTheme`), or `null`. Built here, rendered by `IdleCard` in its body; there is no overlay element and no second window state.
- `StateSwap` (`src/hud/components/StateSwap.tsx`, see its own doc) holds the two bar states and swaps them with the frost-and-spring interstate, keyed on `take = recording || saving`; its `onSettled` sets `takeShown`. The take pill is its `pill` (`src/hud/components/TakeBar.tsx`, see its own doc): while a take runs or saves, the title bar and the row are not rendered at all; the `.hud` root takes the `as-take` class once the pill is shown, which rounds its surface into the 60px pill. Every prop is this component's own state (`paused`, `saving`, `savePct`, `elapsed`, `warn`, `micOn`/`sysOn`, `audio.live`/`audio.read`, `cam.ref`/`camOn`/`cam.on`, `toggle`, `togglePause`, `sourcesOpen` and the Sources toggle).
- `SourcesSheet` (`src/hud/components/SourcesSheet.tsx`, see its own doc), rendered as `TakeBar`'s SIBLING inside the same `pill` slot while `sourcesOpen`, so it hangs under the pill without touching the pill's own layout. Its three pickers are wired to `src.switchDisplay` / `src.switchCamera` / `src.switchMic` through `chrome.picked`, which runs the switch and then closes the menu, the display list and the sheet in one go - a pick applies at once and returns the user to the take.
- The idle card, `StateSwap`'s `idle`: `<IdleCard .../>` (`src/hud/components/IdleCard.tsx`, see its own doc), fed this component's state and handlers - `banner` (`err ?? exportErr`), `exporting`/`pct`, the five header handlers (`openExistingProject`, `openPanel` for Preferences and Settings, `win.minimize`, `handleClose`), the webcam ref and live flag, the camera options (labels through `cleanDeviceLabel`, `src/hud/devices/selectDevices.ts`, which strips Windows/cpal's device-name packaging, e.g. `"Microphone (3- Insta360 Link 2C)"` -> `"Insta360 Link 2C"`), the targets and the mic options, `chrome.menu`/`chrome.toggleMenu`, `chrome.sheet`/`chrome.setSheet`, `chrome.panel`/`panelBody`, the four toggles with `flip` (a setter table keyed by `Toggles`, from `SourceToggles.tsx`), and `toggle` as `onRecord`.

### Notes

- `MotionConfig reducedMotion="user"` wraps the entire tree; all Motion animations (including the pill's breathing dot and the Paused pulse) disable automatically when the OS has reduced-motion enabled.
- The Open Project, Preferences and Settings buttons are conditionally rendered (not just disabled) while exporting; during a take the whole title bar is gone, so there is nothing to disable.
- The card's header stays on screen while a panel is open (it is above the body, exactly as it is over the display picker), so Settings can be swapped for Preferences, minimized or closed without going back first.
