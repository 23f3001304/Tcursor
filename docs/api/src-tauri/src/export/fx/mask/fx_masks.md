# src-tauri/src/export/fx/mask/fx_masks.rs

Turns the mask regions stored on the edit document into the rectangles one frame actually draws. A mask is authored in **canvas fractions** - `[x, y, w, h]` in 0..1 of the RECORDED canvas, not of the stage and not of the output - so it survives a zoom, a layout change and a different export size. This file is the one place that fraction becomes output pixels, and `maskPreview.ts` is its TypeScript twin.

**The twenty-four row table.** `masks_at_projects_a_canvas_rect_through_the_scene` (in `fx_masks_table_tests.rs`) pins the projection over four rects, three camera poses and two layouts. Those numbers are GENERATED by the `#[ignore]`d `print_mask_parity_table` beside them - `cargo test --lib print_mask_parity_table -- --ignored --nocapture` - and pasted verbatim; nobody hand-edits a row. `src/editor/stage/mask/maskPreview.test.ts` pins the SAME twenty-four numbers on the preview side, which is what makes a divergence between the two projections a failing test rather than a look bug.

*Why the tests are two files:* the generated table plus its generator is one responsibility and the behaviour of `masks_at` is another, and together they exceed the 320-line test budget. `fx_masks_tests.rs` holds the fixtures and the behaviour tests and declares `fx_masks_table_tests.rs` as a nested module, the shape `edit/ops/api_tests.rs` already uses for its five siblings.

## HIDDEN_PANEL_ALPHA

```rust
pub const HIDDEN_PANEL_ALPHA: f32 = 0.5;
```

The screen-panel alpha below which the panel counts as not drawn, so no mask on it is drawn either. A camera-only layout fades the screen panel out; a blur that kept painting over the webcam while the screen it belonged to was gone would be a rectangle of nothing. Mirrored by `maskPreview.ts`'s constant of the same name.

*Why a threshold rather than `> 0.0`:* the panel alpha eases across a layout change, and a mask that vanished at the first frame of the fade (or survived to the last) would pop. Half way through the cross-fade is the one point where neither reading is wrong.

## MaskDraw

```rust
#[derive(Clone, Copy, Debug, PartialEq)]
pub struct MaskDraw {
    pub mn: [f32; 2], pub mx: [f32; 2], pub r: f32, pub feather_px: f32,
    pub amount_px: f32, pub dim: f32, pub kind: u32, pub alpha: f32,
}
```

One mask as this frame draws it. **Every length is in OUTPUT PIXELS** - there is no fraction left on this struct, which is what lets `maskdraw` and `fx_uniforms::pack_masks` consume it without knowing anything about the scene.

- `mn`, `mx` - the projected rectangle's top-left and bottom-right corners, already intersected with the screen panel. May lie outside the frame under a zoom; the renderers clamp their own loops.
- `r` - the corner radius, a fraction of the projected rect's SHORT side (so a wide rect does not get ends rounded off) times `roundness`, clamped to 0.5.
- `feather_px` - the soft-edge width, `oh * feather`. The renderers divide the signed distance by it, so 0 gives a hard edge and a large value a wide gradient.
- `amount_px` - blur radius or pixel cell size, `oh * strength`. Scaling by the output height rather than by the rect is what keeps a blur the same strength whether the region is large or small.
- `dim` - how far Highlight darkens everything OUTSIDE the rect, 0..1. Unused by Blur and Pixelate.
- `kind` - `mask_kind_id`'s number: 1 Blur, 2 Pixelate, 3 Highlight. **0 is the empty marker**, which is why the GPU uniform block needs no count field.
- `alpha` - this region's own fade at this instant, from `region_alpha`.

## mask_kind_id

```rust
pub fn mask_kind_id(kind: EffectKind) -> u32
```

The numeric id a mask kind travels to the GPU as: `Spotlight` 0, `Blur` 1, `Pixelate` 2, `Highlight` 3. `fx_mask.wgsl`'s `MK_BLUR` / `MK_PIXELATE` / `MK_HIGHLIGHT` constants mirror these exactly and `maskPreview.ts`'s `KIND_ID` table mirrors them again.

*Why Spotlight maps to 0 rather than being rejected:* 0 is the empty-slot marker in the uniform block, and a spotlight is exactly the thing that is not a mask - one value serves both meanings and no slot can be half filled. `masks_at` filters spotlights out before this is ever reached on a real region.

## masks_at

```rust
pub fn masks_at(effects: &[EffectRegion], scene: &Scene, cam: Camera, src_full: RectF,
                ow: u32, oh: u32, region_t: u32, default_dim: f32) -> Vec<MaskDraw>
```

Every mask live at output time `region_t`, in the order they must be drawn.

### Inputs

- `effects` - the document's effect regions, already on the OUTPUT clock (`EditState::load` runs `remap_doc` first), spotlights included and filtered out here.
- `scene` - this frame's panels and source span. `scene.screen.rect` is where the screen panel sits, `scene.src` is the slice of the recorded canvas being shown (which is how a mid-take display switch moves a mask off the picture).
- `cam` - the camera pose, applied after the panel mapping.
- `src_full` - the WHOLE recorded canvas as a rect, `coordmap::full_src(sw, sh)`. The mask's fractions are fractions of this, never of `scene.src`, which is what makes a mask stay put when the live display changes.
- `region_t` - output-clock milliseconds, for the fades.
- `default_dim` - `settings.clickfx.spotlight_dim`, the fallback a Highlight with no `dim` of its own takes, so the two dimming effects agree unless the user says otherwise.

### Returns

A `Vec<MaskDraw>` sorted by `(layer, index)`, possibly empty.

*Why every live region is returned rather than a winner:* the spotlight uses `SpotlightSim` to elect ONE region and ease alpha across a handoff, because two spotlights at once is a lighting contradiction. Masks are the opposite: two blurs over two different passwords must both be blurred, so **alpha here is strictly per region** (`spotlight_sim::region_alpha`, the same fade ramp, without the simulator) and `SpotlightSim` is never consulted. Sorting is by layer so a Highlight authored above a Blur dims over it, with the array index breaking ties so the order is stable across frames.

### Implementation

1. If `scene.screen.alpha < HIDDEN_PANEL_ALPHA`, return empty (see that constant).
2. Keep the regions whose `kind.is_mask()`, tagged with `(layer, index)`, and sort.
3. For each: `region_alpha` at `region_t`; drop it at alpha 0 and drop one with no `rect`.
4. Project the rect - see below - and drop it if nothing is left.
5. Read the look off the region, falling back to `DEFAULT_BLUR` / `DEFAULT_PIXEL` by kind, `DEFAULT_MASK_ROUNDNESS`, `DEFAULT_MASK_FEATHER` and `default_dim`.

**The projection chain.** All FOUR corners of the rect go through `coordmap::to_panel` (recorded canvas to panel pixels, via `scene.src`) and then `coordmap::project` (panel pixels to output pixels, via the camera crop), and the result is their axis-aligned bounding box. *Why four corners and not two:* the camera never rotates, so the bounding box of the four IS the projected rectangle exactly, and four makes that obvious to the next reader instead of resting on an invariant stated nowhere.

The box is then intersected with the screen panel's own projected rect, and a result thinner than one pixel in either axis is dropped entirely. That is what makes `a_rect_projected_off_the_panel_is_clipped_away` true: a mask placed over display A while display B is the live source projects outside the panel and draws nothing, rather than smearing onto whatever is at those coordinates now.

*A note on the camera scale.* `coordmap::crop` rounds the crop box to whole pixels, so a 2.2x pose widens a span by `1920 / round(1920 / 2.2)` = 2.19931 on x and `1080 / round(1080 / 2.2)` = 2.19959 on y, not by a literal 2.2. That is the camera the export actually uses, and the generated table carries those numbers rather than the ideal ones.
