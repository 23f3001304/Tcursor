# src/editor/stage/Stage.tsx

The preview stage: one live composited preview, and nothing else. The screen (a low-res proxy) and webcam play in hidden native `<video>` elements, a hidden `<audio>` plays the mixed preview audio, and `useCompositeLoop` runs the one `requestAnimationFrame` loop that composites each frame onto a 2D canvas via `drawPreview` plus the backend FX overlay blitted on top. Native decode + `drawImage` holds 60fps. Clicking the canvas adds a zoom focused on the clicked point. This file is the component: the element refs, the media-error state, the pointer wiring and the markup. The engine behind it - the mirrored refs, the invalidation effects, playback, the exact frame and the composite loop - is [useStageEngine](useStageEngine.md); the prop contract is [stageProps](stageProps.md), the hidden media markup [StageMedia](StageMedia.md), and the cursor-style resolution [stageCursor](stageCursor.md).

## Stage

**Look pass (2026-09-14).** Two changes, both from the owner's read that the centre was busy and the preview was not dominant enough. First, the floating toolbar that used to sit over the preview's top edge (`StageToolbar`, `.e-ftool`) is **gone** - not moved: its aspect cycle was a second copy of `Transport`'s own chip and its Cursor/Captions/Camera buttons were second copies of three `Rail` buttons, so relocating it would only have moved four duplicate controls somewhere else. Nothing floats over the preview now. Second, the frame itself: `.e-stagewrap`'s padding drops from 26px to 12px and `.e-stage` trades its 70px black halo for a `--e-line` hairline plus `--e-shadow-1` (see `stage.css`, which is where the stage/transport/rail rules now live).

**View modes.** `useViewMode()` (`viewMode.ts`) supplies Fit (default), Fill or 100%, and `stageFrameStyle(view, canvasW, canvasH, ...useFrameSize(wrap))` turns it into the stage's inline box; `wrap` is a new ref on `.e-stagewrap`, measured by one `ResizeObserver`, and the wrapper takes a `fill` class in that mode. The control is `ViewPicker`, in the transport's right group. Fit is exactly the behaviour this file always had, and the stage box remains the canvas' displayed box in every mode - the invariant every on-stage overlay depends on. See `viewMode.md` for the geometry and for why the mode is a small module store rather than lifted state.

**Time remap.** `map: TimeMap` is a new prop (from `SlotProps`); `layoutSegs`, `cameraMoves`, `zooms` and `effects` now arrive from `outDoc` (the output clock) while `timeMs` stays clip time. The stage derives `tOut = outOf(map, timeMs)` once per render and reads the camera track (`camAt`) for the zoom reticle and click targeting, the Move-mode handle and `useStageInvalidation` (video-background sync, camera-draft discard) at `tOut`; the composite loop gets the same map through `mapRef`. The cursor-style resolution is `stageCursor`, below, unchanged.

**Pointer extraction (M4 T4, plan item A12).** `targetUnderPointer`, `onCanvasClick`, the `useReticleDrag` call and the reticle's own derivation all live in `useStagePointer` (`./useStagePointer.md`). No behaviour changed - the paragraphs below still describe what happens, that hook is just where it happens.

```tsx
export const Stage: React.MemoExoticComponent<(props: StageProps) => JSX.Element>
```

`React.memo`'d (render hygiene pass) - still re-renders every tick while playing (`timeMs` genuinely drives the reticle position and the paused-idle dirty-tracking effect), but skips a re-render from unrelated `Editor` state as long as the caller passes stable callback props.

Composites and shows the current preview frame, driven by the native `<video>`'s clock while playing and by `timeMs` while paused.

**Empty state.** With no `src` and no error, renders `<StageEmpty />` - the wave motif's horizon line with the brand dot landing on it, over "Preparing preview". Its own component (`StageEmpty.tsx`) rather than the inline `Spin` branch it replaced, because this file sits at its line cap; `Stage` still renders one element for it. The recoverable media-error card (`StageMedia`'s `.e-media-err`) is unchanged and still wins over this.

### Props

One prop object, `StageProps`, declared in `stageProps.ts` and documented there - it is the contract `ClassicShell` fills from `SlotProps`, and both this component and `useStageEngine` take it whole rather than re-listing forty fields twice. `Stage` reads it as `p.x` and passes it straight down.

### Behavior

**The engine.** Everything that drives the picture - the mirrored refs, `useStageInvalidation`, `useMediaPlayback`, `useExactFrame` and `useCompositeLoop` - is one call to `useStageEngine(p, { screen, screenB, webcam, audio, canvas }, canvasW, canvasH)`. See [useStageEngine](useStageEngine.md) for what each of them does and why. It hands back what the markup needs: `arrange`, `arranging`, `dirtyRef`, `tOut`, `wantsScreenB`, and the five refs `useStagePointer` and the media handlers read. `screenB` (Batch 4 T7) is the fifth element ref, created here like the other four and rendered by `StageMedia` only when `wantsScreenB` says this document can actually dissolve a clip boundary; the component itself never touches the element.

**Click-to-zoom / click-to-aim (`onCanvasClick`, now in `useStagePointer`).** One shared `targetUnderPointer` helper delegates to `mapCanvasClickToZoomTarget` (`zoomTargetMapper.ts`), which un-projects the pointer through the current whole-frame zoom crop back to a 0..1 screen-content fraction. The result then goes to `onAimAt` in aim mode, else `onZoomAt` - the two are mutually exclusive meanings for the same click. Clicks outside the screen rect (on the background or PiP) are ignored (`null`).

**Aim reticle (`reticle` + `onReticleDown`).** When `aimPoint` (or the drag-live `liveAim` below) is set and playback is paused, `mapZoomTargetToCanvasPoint` projects that target back onto the canvas for THIS frame (the crop moves it as a zoom ramps) and `ZoomReticle` renders there. It is hidden during playback on purpose: it is an editing affordance, not a playback overlay, and a spring chasing a per-frame camera would read as lag. In aim mode the reticle is draggable - pointer-down stops propagation and attaches `attachPointerGesture` (`pointerGesture.md`); `useReticleDrag` also stashes its `detach` in a ref and releases it on unmount, so Stage unmounting mid-drag can't leave the gesture's window listeners bound forever (bug-sweep-2 Task 8, L4). There is **no** new undo machinery: each committed move is an ordinary `update_zoom`, so `useEditHistory`'s `COALESCE_MS` window already folds a whole drag into one undo step.

**Reticle drag debounce (render hygiene pass, extracted to `useReticleDrag` in fix round 2 - purely to keep this file under its line budget).** `onAimAt` is a full `apply_edit_op` round trip that cascades into `camera_track`/`previewLayout` refetches on the doc's `rev` bump - calling it on every pointermove was one of the per-pointermove IPC storms this pass targets (finding F#2/#5). `const { liveAim, aimDrag, onReticleDown } = useReticleDrag(aimPoint, onAimAt, targetUnderPointer);` owns the whole thing now; see `useReticleDrag.md` for the full write-up (the debounce itself, the fix-round-1 ghost-override fix via the shared `shouldClearOverride`, and the fix-round-2 `pointercancel` fix via `attachPointerGesture` - see `pointerGesture.md`). `Stage` itself now only derives `shownAim = liveAim ?? aimPoint` and the resulting `reticle` screen position from the hook's return.

**AI review outline.** `<StageOutline rect={outline} ... />` is rendered unconditionally, just under the reticle, and paints only while `outline` is non-null - always-mounted is what keeps its `AnimatePresence` exit alive so the box fades out. See `StageOutline.md` for the projection and the punch-through dim.

**Mask drag box (batch 2a).** Delegated entirely to `MaskOverlay` (see `mask/MaskOverlay.md`) and `useMaskDrag` (`mask/useMaskDrag.md`), rendered while `mask.box && !arranging && !p.moveMode`. It is the FOURTH exclusive stage pointer mode beside aim, Move and arrange, and it is gated the same way they are: the hook itself is handed `null` unless this mode owns the pointer, and this JSX guard is the visible half of that. No drag logic lives in this file - the box is one sibling element and the engine returns everything it draws.

**Move-mode drag.** Delegated to `CamDragHandle` (see `CamDragHandle.md`), rendered only while `moveMode` is on (passed `playing` as a new prop, see below). `Stage` keeps just one half of the draft lifecycle: its `[timeMs]` effect clears the shared `camDraftRef`, which must happen even when Move mode is off and the handle is unmounted - UNLESS the change is just the composite loop's own natural playback progress (`isNaturalPlaybackTick`, `./transport/playback.ts`), not an actual seek/scrub (bug-sweep-2 Task 8, M6; redesigned in review round 1, Important 3 - the original `camDraggingRef`/`draggingRef`-gated version only protected the draft WHILE a drag was actively in progress, so the very next tick after releasing the pointer still nulled it - "Add keyframe at playhead" could still write frame-centre if pressed even slightly after letting go). `lastCamTimeRef` tracks the previous `timeMs` this effect saw; `playRef` (from `useSyncRefs`) supplies the CURRENT `playing` without needing it in the effect's own dependency array (which stays `[timeMs]`-only, matching the pre-existing pattern).

**Frame-tool strip: removed.** `StageToolbar` and its `.e-ftool` rules are deleted - see "Look pass" above for why relocating four duplicate controls was not the fix.

**Raw→proxy swap.** `onLoadedMetadata` reports the duration, restores `currentTime` from the ref, and resumes playback if it was playing - so swapping `src` from the raw capture to the proxy doesn't snap the playhead to 0.

**Media-error retry.** On Retry (`StageMedia`'s error card), `Stage` clears its own `err` (so the card disappears immediately rather than waiting for a reload to actually succeed), calls `onRetryMedia()` (may re-run `ensureProxy` on the backend), AND calls `screen.current?.load()` directly on the native `<video>` element. The `.load()` call is necessary because `srcUrl` is deterministic - `planProxySrc` resolves to the exact same filename on retry whenever the `immediate`/`known` branches apply, so merely re-running the effect and calling `setSrcUrl` with an unchanged string is a React no-op (`Object.is`-equal, no re-render, no DOM change) that would never actually re-attempt loading. `HTMLMediaElement.load()` is the platform API for "reload the resource at the current `src`", so it works regardless of which `planProxySrc` branch produced that `src`.

### Notes

- The canvas backing store follows `layout.canvas` (from `PreviewLayout`, resolved server-side via `Layout::resolve` from `EditDoc.aspect`) - `DEFAULT_CANVAS` (1280x720) is only the pre-load fallback. `.e-stage`'s box is set inline from the same `[canvasW, canvasH]` (via `stageFrameStyle`, which in Fit is just that pair as an `aspect-ratio`) so the stage box, the canvas, and every fraction in this file share one basis regardless of the chosen aspect or view mode. CSS then scales that box to fit; `onCanvasClick`/`mapCanvasClickToZoomTarget` divide by the displayed rect to recover backing-store pixels.
- The spotlight/click-FX overlay is rendered by the backend at pixel-perfect parity with the export (not approximated in Canvas2D) - see `previewCanvas.md`, `fxOverlay.md`, `useCompositeLoop.md`.

### `data-ui-fx="off"` on the stage frame (micro-interaction pass, 2026-09-14)

`.e-stage` carries `data-ui-fx="off"`, which opts the whole preview frame - canvas, reticle, cam drag handle, arrange overlay, media-error card - out of the editor's click ripple. See [ripples](../effects/ripples.md) for how the attribute is read and [InterfaceEffects](../effects/InterfaceEffects.md) for the overlay itself.

Two reasons, and the first is the one that matters: **the frame owns its pointer outright**. A pointerdown here means add a zoom, aim a zoom, drag the reticle, drag the PiP handle, or drag an arrange panel - never "press a control". A bloom would fire on the first frame of every one of those gestures. And the surface it would bloom over is the composited video, which is the one thing in the app that must show exactly what the export shows and nothing else.

The attribute sits on `.e-stage` (the frame) rather than on `.e-stagewrap` (the well it floats in), so a click on the well around the frame still ripples like any other editor ground.
